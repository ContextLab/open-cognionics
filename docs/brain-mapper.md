# brain-mapper

`brain-mapper` is a second Python package in this repository (`brain_mapper/`, a uv workspace member). It is a local web app built on the public API of `open_cognionics`. It starts a server and serves the participant page: a start screen, the setup screens (participant ID, device setup, calibration), the five task rounds (words, perception, 2-back, flanker, spatial memory) and the delayed free recall, the video round (an embedded Vimeo video, the one thing a page loads from another host; see "Video"), the rest screens, between-blocks screens and the summary; every session ends in a zip of its folder. An onlooker window (`/onlooker`) shows the live display beside the participant's page.

## Running

```bash
uv run brain-mapper --replay <recording>        # from a saved recording
uv run brain-mapper --port <serial device>      # from a headset
```

The command prints `brain-mapper at http://127.0.0.1:<port>` on one line and then opens the default browser.

| Option | Meaning |
|-|-|
| `--port PATH` | Serial device of the headset. |
| `--replay PATH` | Saved recording to play back. |
| `--data-dir DIR` | Where sessions are kept, in `<DIR>/sessions/`. Default `~/brain-mapper`. |
| `--http-port N` | Port on 127.0.0.1. Default 8740; the next free port is used if it is taken: a port is taken when a TCP connection to `127.0.0.1:<port>` or `[::1]:<port>` is accepted within 0.3 s (so a listener on `0.0.0.0` or `::` counts), and the socket is then bound with `SO_REUSEADDR` (not on Windows), so a restarted app gets back a port whose connections are in TIME_WAIT. `0` lets the operating system choose. |
| `--flow FILE` | Session flow file. |
| `--no-browser` | Do not open the browser. |
| `--check` | Print one line per start-up check and exit: 0 if every check passes, 1 if not. Opens no serial port, writes no byte to any device and installs nothing (see "Start-up checks"). |

The server listens on 127.0.0.1 only. Every request needs a `Host` header of `127.0.0.1:<port>` or `localhost:<port>`. Websocket upgrades and every request that is not a GET also need an `Origin` of `http://127.0.0.1:<port>` or `http://localhost:<port>`. Other requests get status 403. Ctrl-C stops the process; a session under way is ended and zipped first (see "Session zip").

Routes: `/` (participant page), `/onlooker`, `/static/...`, `/api/health` (`{"ok": true, "version": ...}`), `/api/flow` (the steps of the session as JSON, `[{id, kind, title, module, blocks: [{id, seconds, points}], calibration}]`; `calibration` is `null`, or for the calibration step `{eyes_open, eyes_closed, blink_cues, blink_gap, blink_lead, blinks}` in seconds), `/api/participants` and `/api/participant` (see "Participant ID" below), `/api/import` (see "Saved session files" below), `/api/progress` (see "Skip, stop, one round, continue" below), `/api/session/zip` (see "Session zip" below) and the websocket `/ws`. Like every route, they need a `Host` of `127.0.0.1:<port>` or `localhost:<port>` and answer 403 otherwise.

`--port` and `--replay` cannot be used together. The source is opened on a thread after the server starts, so a headset that cannot be opened does not make the command exit: the page is told what the last attempt came back with (the `problem` of the `link` message, see "Device setup" below) and the attempt is repeated every 2 seconds. A replay that cannot be opened is reported as an `error` message and a `link` with state `ended`, and not tried again.

## Start-up checks

`brain_mapper.checks.run(settings)` returns one `Check(id, ok, text, fix)` for each of these, in this order, and `brain-mapper --check` prints each as one line (`PASS  <id>: <text>` or `FAIL  <id>: <text> Fix: <fix>`; every line starts with `PASS` or `FAIL`, except the `video_host` line below, which can start with `WARN`). The server runs the same checks when it starts, prints each failure to standard error, and sends the list to every page as `{"t":"checks","items":[...]}`; the start screen shows the failed ones with their fix. A failed check does not stop the server. With `--check`, an argument error (including one that argparse reports) also prints a line `FAIL  arguments: <problem>` on standard output and the exit status is not 0.

|`id`|What is looked at|
|-|-|
|`python`|The Python version is 3.10 or newer.|
|`open_cognionics`|The package imports; its version is in the text.|
|`page_files`|Every file under `web/` except `web/vendor/three/` is present and has the sha256 recorded in `brain_mapper/src/brain_mapper/web_files.json`. A changed, missing or unrecorded file is named.|
|`three_js`|The same for the files under `web/vendor/three/`.|
|`data_folder`|A small file can be made in the data folder, and is removed again. A folder that does not exist yet is not made: its nearest existing parent is tried instead.|
|`dongle`|`oc.find_headsets()` lists the ports that look like the headset dongle. It lists serial ports and opens none; no dongle found is reported as a pass, since a replay needs none. The port given with `--port` is not opened.|

The recorded hashes cover every file under `web/` (names starting with a dot are left out). After changing any file there, make the list again with `uv run python scripts/brain_mapper_web_hashes.py` and commit `web_files.json`; `scripts/brain_mapper_web_hashes.py --check` exits 1 if the list is out of date, and `test_the_recorded_list_is_what_the_web_files_hash_to` in `tests/brain_mapper/test_checks.py` fails until it has been made again.

After those lines `brain-mapper --check` prints one more, `video_host` (`checks.video_host()`): it sends a `HEAD` request to `https://player.vimeo.com/` (user agent `brain-mapper-check`, nothing of any session, a 5 s limit). Any HTTP answer, whatever its status, gives `PASS  video_host: player.vimeo.com answered (HTTP <status>); only the video round needs it.` No answer is a warning, never a failure: `WARN  video_host: player.vimeo.com could not be reached (<reason>). Only the video round needs it: it shows the video from there; every other part of the session works without the internet. Fix: Connect this computer to the internet before the video round, or skip that round.` A warning does not change the exit status. The server does not run this check when it starts (so it never waits on the network), and the `checks` message does not have it.

## setup.sh

`./setup.sh [--yes]` (macOS and Linux) prepares a fresh checkout and prints one `PASS` or `FAIL` line per step:

1. `uv`: if it is missing, the script asks before installing it (`--yes` answers yes; no answer or an end of input is a no). On a no it prints `curl -LsSf https://astral.sh/uv/install.sh | sh` and exits with status 1.
2. Rust: `cargo --version`. If `cargo` is missing the script prints the rustup command and exits with status 1; it installs nothing. Then `CARGO_BUILD_JOBS=4 uv sync --locked`, which builds the Rust extension and installs the default dependency groups, the same set `uv run` keeps in place (the documentation group is not installed). `uv.lock` is not changed.
3. `uv run --locked brain-mapper --check`, whose lines each start with `PASS` or `FAIL`. On Linux the script also reports when the serial device (`/dev/ttyACM*` or `/dev/ttyUSB*`) belongs to a group the user is not in, and prints `sudo usermod -aG <group> "$USER"`; that part is written from documentation and has not been run on Linux.
4. The last line is the command that starts the demo, `uv run brain-mapper`.

The script does not use `sudo`, does not edit shell profiles, does not open a serial port and writes only in the repository and in uv's folders. A second run changes nothing. `tests/brain_mapper/test_setup_script.py` runs the real script.

## Sources

`brain_mapper.source` has two classes with the same interface. `LiveSource(port)` reads the headset with `open_cognionics.connect` and `Headset.stream`; `ReplaySource(path)` plays a recording with `open_cognionics.replay(..., realtime=True)`. A replay path is a session zip (its `eeg/` folder is used), a session folder (or a folder that holds `eeg/`), or a `raw.bin` with `meta.json` beside it. A `raw.bin` alone is refused, because the headset configuration that decodes it is in `meta.json`.

Each source reads on one thread, which starts with the first `subscribe(maxsize)`. Every subscriber has its own bounded queue; a chunk that does not fit is dropped for that subscriber only. The last item in a queue is a `SourceEnded` with a reason: `disconnected: ...` when the headset link drops, `silent` when the hub ended a link that sent nothing for 3 s (`drop_link`), `end of recording` at the end of a replay, `stopped` after `stop()`.

`LiveSource.connect_with_retry(report)` calls `open()` until it works, one attempt at a time on the calling thread: a failed attempt is passed to `report(problem, attempt)` (a `LinkProblem` made by `describe` from the `open_cognionics` error: `code` is `no_headset`, `several_headsets` with the ports listed, `open_error`, `no_data`, `no_configuration`, `disconnected` or `other`) and the next attempt starts 2 seconds (`RETRY_SECONDS`) after the failed one ended, so a slow attempt is never followed at once by another and `stop()` ends the wait at once. An attempt works only once samples flow: `open_streaming()` is `open()` and then a wait of up to `SILENT_SECONDS` (3.0 s) for the library to decode the first sample after the configuration reply; with none the port is closed and the attempt fails with `NoData`. `drop_link(reason)` ends an open link as a lost one (the port is closed, the reader ends with `SourceEnded(reason)`); the hub calls it with `"silent"` when no chunk has come for `SILENT_SECONDS`. `reset()` makes an ended live source ready to be opened again. `decoded` is the number of samples the library has decoded so far (whole packets and lost ones).

`start_recording(directory, participant, participant_uuid)` on a live source calls `Headset.record`. On a replay it copies `raw.bin`, `meta.json`, `clock.jsonl` and `recording.bdf` of the source unchanged and writes the marks of the run to a new `markers.jsonl` with `sample` equal to the samples read so far. `mark(label)` adds a marker and returns the sample number it was given; `stop_recording()` closes the recording. When the link ends (the headset disconnects or the replay reaches its end) the source closes the recording itself and, for a headset, closes the port; `stop()` does the same on request, closing the headset first so that every byte the library received is in `raw.bin`. `stop()` while `open()` is still waiting for the headset is safe: `open()` closes its connection when it returns and raises `RuntimeError`. The properties `recording` and `released` report whether a recording is open and whether the port is free. `set_contact_check(on)` sends byte `0x11` or `0x12` through `Headset.impedance_check` on a live source and does nothing on a replay.

## Websocket messages

Server to page, JSON text:

|Message|Meaning|
|-|-|
|`{"t":"hello","fs","labels","kind"}`|Sample rate, the 20 EEG labels, `"live"` or `"replay"`. Sent each time the source has opened; the participant connection gets `name` for a replay, an onlooker never does (a replayed session folder is named after its participant label). For a replay it also has `name`, the file name (not the path) of the recording.|
|`{"t":"link","state","reason","recording","problem"}`|`state` is `connecting`, `live` or `ended`; `reason` says why it ended. `recording` says whether the recording has started. `problem` is `null` or `{"code","kind","msg","ports","dropped","attempt","retry_s"}`: the error the last attempt to open the headset, or the read of its link, came back with (`code` as in `LinkProblem`, `kind` the name of the `open_cognionics` error, `msg` its text, `ports` the ports a `SeveralHeadsets` lists, `attempt` the number of the attempt, `retry_s` 2). While `problem` is set the state is `connecting`. `dropped` is true when a link that was live was lost and has not come back. `ended` is sent for a replay that ran out and for a live link lost after the device step. `fault` is true on an `ended` that the hub thread's own failure caused.|
|`{"t":"status","rate","lost","lost10","bat","imp"}`|Sent to every client once a second while the link is live. `rate` is rows received a second over the last 2 seconds (`null` in the first second), `lost` the samples lost since the link opened, `lost10` those lost in the last 10 seconds, `bat` the battery reading in volts as read (`null` if not a number), `imp` whether the contact check is on.|
|`{"t":"checks","items":[{"id","ok","text","fix"}]}`|The start-up checks, sent on connect (see "Start-up checks").|
|`{"t":"trace","hz":50,"x"}`|EEG for drawing only: `x` is rows of 20 numbers in microvolts at 50 rows a second (the mean of every 10 input rows at 500 Hz; rows of lost samples are left out of the mean), 5 rows to a message, so 10 messages and about 7 kB a second. Sent only to a client that sent `{"cmd":"display","on":true}`, which the device screen does while it is shown. Each client may have 100 of them waiting (10 seconds); older ones are dropped. It changes nothing that is recorded.|
|`{"t":"error","kind","msg"}`|`kind` is the name of the `open_cognionics` error (for example `OpenError`), `bad_message`, `bad_command`, `refused`, `second_window`, `folder_not_locked`, `replaced` (a command from a participant connection that a newer one of the same page replaced; it was not run) or `bad_event` (with the event's `cid`, see "Tasks", "Payload keys").|
|`{"t":"ack","cid",...}`|The answer to a page event that carried a `cid`: `seq` once it is in `events.jsonl`, or `late`, `dropped` or `refused` (see "Tasks", "Delivery"). Sent only to the participant connection that sent it.|
|`{"t":"d","x","lost","bat","imp"}`|`x` is rows of EEG in microvolts, `lost` the samples lost before the chunk, `bat` the battery volts, `imp` whether the contact check is on. Sent only to a client that has sent `{"cmd":"traces","on":true}`; `{"cmd":"traces","on":false}` stops it.|
|`{"t":"state", ...}`|The session state (see below): sent to every client when a client connects and on every change, and again to each client that has been sent none for a second (counted per client).|
|`{"t":"contact","states","good","check","settling","sample","error"}`|Once a second while the contact check is on (see "Calibration"): `states` is `{label: "good"|"marginal"|"bad"}` over the last second, `good` the number of good ones, `check` the `contact_check` of the state the measure belongs to, `sample` the number of the sample after the last one measured. Until the first measure of the check, `states` and `good` are `null` and `settling` is true (the first second after `0x11` is left out). `error` says why the contact cannot be measured at the headset's sample rate, else `null`.|
|`{"t":"points","total","gained","block","reason"}`|Sent once when a block has ended and earned points, right after the `state` whose phase is `between`. `total` is the new total, `gained` the points of that block, `block` the block id. Never sent while a block runs or is paused.|
|`{"t":"package","state","folder","file","msg","summary","notes","download","results"}`|The session zip, once the session is over: `state` is `making`, `saved` or `failed`. Sent only to the participant connection, never to an onlooker. See "Session zip" below.|

A client that connects later is first sent the current `hello`, `error` and `link` messages (and the last `package` message, if there is one) and then the current `state`. Each client has its messages waiting in two lanes (`server.Lanes`): the drawing data (`d`, at most 1000 waiting, and `trace`, at most 100; newer ones are dropped when full) and everything else, which is never dropped. The lane of what is never dropped is always emptied first, in its order, so a `state` never waits behind drawing data however slowly a page reads; the drawing data follow in their order. Each client has its own sender, so a slow client does not hold up another (measured 2026-11-25: at most 2 ms from the engine's change to the onlooker socket's send). A message that is not a JSON object gets a `bad_message` error and the socket stays open.

Page to server: `{"cmd":"traces","on":true|false}` (any client; raw rows as `d`), `{"cmd":"display","on":true|false}` (any client; the thinned `trace` rows), and the session commands `{"cmd":"advance"}`, `{"cmd":"pause","reason":"..."}`, `{"cmd":"resume"}`, `{"cmd":"skip","step":"<id>"}` (`step` is optional), `{"cmd":"stop"}`, `{"cmd":"check_again"}` (see "Calibration"), `{"cmd":"video_ended","step":"<id>"}` (see "Tasks", "Video"), `{"cmd":"block_finished","reason":"participant_done"|"trials_done","step":"<id>"}` (`step` optional), `{"cmd":"headset_check"}` and `{"cmd":"headset_check_done"}` (see "Pause, the headset check and finishing a block early") and `{"cmd":"event","name","payload","browser_time","time_origin","cid","session_id"}` (`cid` and `session_id` optional; see "Tasks", "Delivery"). Session commands are accepted only from the participant connection, `/ws?role=participant`. A connection without a role, or with `role=onlooker`, is read-only: its session commands are ignored. The participant page sends a random page id as the query parameter `page` (`/ws?role=participant&page=<id>`, 1 to 64 of `A-Z a-z 0-9 _ -`) and keeps it across reloads. A participant connection with the same id as the connected one replaces it at once and the old socket is closed. A participant connection with another id, or none, while one is connected gets `{"t":"error","kind":"second_window","msg"}` (the message names `/onlooker`) and is closed; the slot is free again once the connection has closed. A command the engine refuses gets `{"t":"error","kind":"refused"}`, an unknown command `kind` `bad_command`.

## Session flow and engine

`brain_mapper.flow` holds the steps of a session: `Step(id, kind, title, blocks, calibration=None, module=<the id>, video=None, may_finish_early=False)` with `Block(id, seconds, points)`. `default_flow()` is the order of the session design: `participant`, `device`, `calibration` (kind `setup`); `words` (blocks `list1`, `list2`), `perception` (2 blocks), `nback` (2), `flanker` (2), `spatial` (2, title "Spatial memory") (kind `task`); `video` (`video`); `rest_closed`, `rest_open` (`rest`); `recall` (`recall`); `summary` (`summary`). The task blocks have the lengths of spec 6.4 (`flow.TASK_SECONDS`, `flow.TASK_BLOCKS`), except Words: `words` 2 x 145 s (the longest study phase, 52.6 s, and 90 s of recall; see "Words"), `perception` 2 x 60 s, `nback` 2 x 50 s, `flanker` 2 x 50 s, `spatial` 2 x 60 s (2-back, flanker and spatial memory had three blocks until 2026-11-25). The delayed free recall (`recall`, kind `recall`) is one block of 125 s (`flow.RECALL_SECONDS`: a 2 s lead-in and 120 s of recall, spec 6.3: 2 minutes); it shows the task module registered as `recall` (see "Tasks"). The video block (`video`) lasts 165 s (`flow.VIDEO_SECONDS`): the part of the video that is played (`flow.VIDEO`, 11.5 s to 173.5 s of the video's 180 s; see "Video") in whole seconds, and 3 s for the player to start; the two rest blocks last 180 s each (`flow.REST_SECONDS`, spec 6.3: "Rest, eyes closed: 3 min", "Rest, eyes open: 3 min"; until 2026-11-25 they were 10 s placeholders). `words`, `video` and `recall` have `Step.may_finish_early` set (see "Pause, the headset check and finishing a block early"); in a flow file a step gets it with `"may_finish_early": true`. Every block is worth 100 points (`Block.points`). `--flow FILE` reads the same steps from a JSON list (`id`, `kind`, `title`, `blocks` of `id`, `seconds`, `points`, and optionally `module`); `tests/brain_mapper/flows/short.json` is the same flow with 2 s blocks and `"module": null` on its task, video and recall steps, so they keep the placeholder whatever tasks are registered. `module` names the page module (see "Tasks") that draws the step; left out, it is the step id (so every step of `default_flow()` has its id as module); `null` keeps the timed placeholder for that step. A module that is neither `null` nor 1 to 64 of `A-Z a-z 0-9 _` not starting with a digit is refused ("module must be null or 1 to 64 of A-Z a-z 0-9 _ not starting with a digit"). The calibration step of `default_flow()` has `Step.calibration` set (`flow.Calibration`: eyes open 20 s, eyes closed 20 s, 5 blink cues 2 s apart starting 2 s in, so the blinks part lasts 12 s); in a flow file a setup step gets it with `"calibration": {"eyes_open": <s>, "eyes_closed": <s>}`. A video step has `Step.video` (`flow.Video(id, start_s, end_s)`: the Vimeo id and the part played); in a flow file `"video": {"id": <vimeo id>, "start_s": <s>, "end_s": <s>}`, and a video step without it gets `flow.VIDEO`. It is refused on a step of another kind, unless `0 <= start_s < end_s`, and for an id that is not a whole number above 0. `/api/flow` gives it to the page as `video`. A setup step without it is one screen with Continue; `short.json` has none, and the tests of the calibration step add it with 3 s parts. A flow file is refused for duplicate step or block ids, an unknown kind, a `setup` or `summary` step with blocks or points, and a step of another kind without blocks.

`brain_mapper.engine.Session(flow, source, points, clock=time.monotonic, *, folder, meta=None)` owns the current step and block, the block timers and the pause state. Pages draw what it reports and do not run timers. `state()` returns `step`, `kind`, `block`, `phase`, `remaining`, `award` (while the phase is `between`: `{step, block, points, interrupted}` of the block that just ended, as awarded by the ledger, `points` 0 in a session without a ledger or for a block a pause ended (`interrupted` true); otherwise `null`), `blocks_done`, `blocks_total`, `points_total`, `ended_early`, `stopped`, `failure`, `reason` (the reason given to `pause` while the phase is `paused`, otherwise `null`), `plan` (the ids of the steps this session plays, in order), `outcomes` (step id to `finished`, `partial`, `skipped`, `not_reached` or `running`), `blocks_by_step` (step id to the number of its blocks that finished), `substep`, `contact_check`, `calibration` and `cues_logged` (see "Calibration"), `link_down` (true between `link_lost` and `link_back`), `interrupted` (while paused: the id of the block the pause ended, else `null`), `interrupted_blocks` (step id to the ids of its blocks that a pause ended), `headset_check` (`null`, or `{"phase": "contact"|"settling", "check"}` while the headset check of the paused screen is open or going off), `seed` (the session seed of `progress.json`, the one the tasks draw their random numbers from; `null` before a label is accepted), `only` (as in `progress.json`: the rounds chosen on the start screen, or `null`), `session_id` (a random id of 16 hex digits made when the session begins, unique per session and free of the label; also in `session.json` and `progress.json`; `null` before a label is accepted: the page keys everything it keeps in sessionStorage on it, so a later session in the same tab, even one with the same seed, starts clean) and `rev`. `stopped` is true after the participant stopped the session; that is a normal ending (`failure` stays `null`, `ended_early` stays false, phase `done`). A step is `running` only while the session is at it. A round that is left (by `skip`, by `stop`, or because the session ended there) has the outcome `finished` if all its blocks finished (so a skip or a stop on the between screen after its last block leaves it `finished`), `partial` if at least one block finished and some did not (shown as "Partly played"), and otherwise `skipped` (after a skip) or `not_reached` (after a stop or any other ending). `finished`, `partial` and `skipped` rounds count as done: a session that continues this one never plays them again, so no block is paid twice. `meta` is a dict saved in `progress.json`: `session` (the folder name; the folder's own name if left out), `uuid`, `seed`, `continues` and `only` (each `None` if left out) and `session_id` (a new random one if left out). `rev` grows by one with every change; the server sends a state only if its `rev` is not below that of the last one it sent, so a page sees `rev` never go backwards (states sent once a second repeat the current `rev`).

Each command is all or nothing: its line in `events.jsonl` is written first and taken out again if the marker cannot be put (if taking it out fails too, as with a full disk or a file size limit, the file is closed, cut back to where the line began and opened again, so the log never ends in half a line), and then the state, the `seq` and the `rev` are as they were and the command raises. `ended_early` is false when the source ends while the session is at its last step. `phase` is `waiting` (before a setup step is left or a block starts), `running`, `paused`, `between` (a block has ended) or `done`. `kind` is `rest` during the two rest steps, which is what a page uses to hide the points total and progress there.

Commands: `advance()` leaves a setup step, starts the next block, or leaves the between-blocks screen; `pause(reason)` pauses a running block and `resume()` ends the pause, as "Pause, the headset check and finishing a block early" describes (a task or recall block is ended by the pause, and Resume goes on from the between-blocks screen; a rest starts again; the video goes on where it was); `block_finished(reason, step)`, `headset_check()` and `headset_check_done()` are described there too; `event(name, payload, browser_time, time_origin)` saves an event sent by the page; `video_ended(step)` ends the running block of a video step before its time is up (see "Tasks", "Video"); `tick()` ends a block whose time is up and notices that the source has ended. A command the state does not allow raises `CommandRefused`. When the source ends before the last step the session goes to `done` with `ended_early` true.

Every state change and every event puts the marker `<step>/<name>#<seq>` into the recording and appends a line to `events.jsonl` in `folder` with `seq`, `step`, `block`, `name`, `payload`, `browser_time`, `time_origin`, `unix_time` and the other clock fields of "The times of an event line" (see "Tasks"); the marker with the same `seq` gives the sample number. Names the engine uses: `step_start`, `block_start`, `block_end`, `paused`, `resumed`, `session_end`, `skipped` (payload `block`, the block in progress or `null`, `seconds` it had run, `blocks_done`), `stopped` (same payload, and `ended_early` false), `ended` (the session was ended by a failure; its payload has the reason), and `source_ended` (which has no marker, because the recording is closed by then). Page events use the name the page sends (1 to 64 of `A-Z a-z 0-9 _ . -`).

The server starts one `Session` on the source when the first participant label has been accepted (see below) and ticks it every 0.05 s. It records into `<data-dir>/sessions/<label>_<YYYYMMDD>_<HHMMSS>/eeg/` and writes `session.json`, `events.jsonl` and `points.jsonl` in `<data-dir>/sessions/<label>_<YYYYMMDD>_<HHMMSS>/` (`server.make_session_folder(sessions, label, now)` makes the folder with an atomic `mkdir`; a `-2`, `-3` ... is added to the name if it exists, so two sessions started in the same second never share a folder). `session.json` is written when the session begins, by replace-rename: `{"session": <folder name>, "label", "uuid", "started_unix", "source": "live"|"replay", "session_id"}`, `"continues": <the earlier session's folder name>` when the session continues one, and `"only": <round id>` when the session plays that one round alone, or `"only": [<round id>, ...]` (route order) when it plays several chosen rounds (such a session stands apart: it is never offered to continue, and a `continues` that names one is refused with `not_continuable`); each of the two keys is absent otherwise. Every session also has `sample_point` and `previous_sessions`, and a session started from a saved session file has `imported_from` (see "Saved session files"). The hub rewrites it with `"recordings": [{"folder", "samples"}]` when a lost link's recording is set aside (see "Device setup"). When the session is over, more fields are added to `session.json` and the session is zipped beside its folder (see "Session zip"). `progress.json` is written next to it (see "Skip, stop, one round, continue"). It is the one place the label and UUID of a session are read from (a replayed recording keeps its own `meta.json`, and a label is not parsed back out of a folder name). `Hub.participant` is `(label, uuid)` once a label is accepted, else `None`; `Hub.folder` is the session folder. Nothing is recorded before that: the EEG is shown live and is not saved, no folder is created under `sessions/`, and no session exists. The recording starts with the session if the headset is linked, and otherwise when it first is (see "Device setup"). Until then the websocket sends a `state` of the first step, waiting, with `rev` 0 (or phase `done` and `ended_early` true if the source ended first), and every session command is refused with `kind` `refused` ("enter a participant ID first").

## Pause, the headset check and finishing a block early

**A pause ends the running block**: resuming a task part-way after a break would be a different task, so the session goes on with the next block. Any pause of a running block (`pause` from the page: full screen left, the page reloaded, by hand; or the engine's own pause when the headset link is lost or silent) saves `paused` (payload `reason`) and then, for a block of a step of kind `task` or `recall`, ends that block at once: `block_end` with `ended_by: "interrupted"`, `seconds` (how long it ran), `reason` and `points` 0 (no ledger line, no `points` message). The block counts as played: `blocks_done` grows by one at the pause, so `progress.json` and a later Continue treat the round as `partial`, or `finished` when it was its last block, and the block is never played again. Trials finished before the pause stay in `events.jsonl` and in the scores; the trial in progress is abandoned by the page as before. `state.interrupted` names the block while paused, `state.interrupted_blocks` lists every block a pause ended, and the session timeline (`session.json`, the summary) gives such a block the outcome `interrupted` ("(interrupted)" after its length in the summary's timeline, and "1 block interrupted by a pause" under the round's points). Resume (only by a press, and grayed out while no samples flow, as before) saves `resumed` with `{"to": "between"}` and goes to the between-blocks screen; from there the next block starts in the usual way (its instructions, then the task's own start), or, after the round's last block, the next round. A block of a step of kind `rest` is ended the same way but does not count: Resume (`{"to": "block_start"}`) goes back to the rest's start screen and the rest period is played again from its beginning. The video round is one continuous block: it is held at its position and resumes there with the time it had left. A calibration part (eyes open, eyes closed, blinks) starts again from its beginning on Resume whatever the reason of the pause (`part_restarted` with the reason). A pause while nothing runs (an instruction screen, the between-blocks screen) is refused and changes nothing. The pause overlay says what Resume will do: "This block has ended and is not repeated. Press Resume to go on to the next block." (or "... to the next round."), "Resume starts this rest again from the beginning.", "Resume starts this part again from the beginning.", or, for the video, the time left. The between-blocks screen after such a block adds "The last block was ended by the pause; its finished trials still count." A task that starts on Enter (flanker, n-back, perception, spatial memory) shows its own prompt for the next block instead of the between-blocks screen, so that prompt (`#task-ready`) says the same sentence.

**The headset check of the paused screen.** The pause overlay, whatever the reason of the pause, has "Check the headset" (`#fs-check`). It sends `{"cmd":"headset_check"}`: the engine saves `headset_check_start` (payload `reason`, the pause reason) and sets `state.contact_check` to its `seq`, so the hub switches the headset's contact check on (`0x11`) exactly as for the calibration step, and the `contact` messages carry the states of every electrode. The overlay then shows the same contact view as the calibration's contact check (`screens/contact-panel.js`, used by both: the fit view `#hc-view`, the count `#hc-count`, the pills of the contacts that are not good) and "Done" (`#hc-done`, `{"cmd":"headset_check_done"}`), which saves `headset_check_end` with the `states` of the last second measured (`good`, `measured`; `measured` false and `states` `{}` when nothing was measured), switches the check off (`0x12`) and begins the settling wait: `state.headset_check.phase` is `settling` until the data have shown the check off for `SETTLE_S`, counted in samples as after the calibration step; then `headset_check_settled` is saved and, with the hub's signal window (always in the app), the signal check runs exactly as after the calibration's contact check (see "Signal check"): `signal_start` (payload `seconds`, `version`, `for: "headset_check"`), `state.headset_check.phase` `signal` with `signal_left` (seconds), then `signal_end` (the same payload as in calibration, with `for: "headset_check"`). The result is shown on the paused screen in `#fs-signal` ("Signal check: 20 of 20 contacts good; 1 channel noisy: Fp1", the words of the calibration's signal check; from `state.headset_result`, `{states, signal}`), with `#fs-signal-warn` when a channel is not fine, until Resume or the next check, and it is added to the check's entry in `calibration.json` as `signal`. The overlay is then back to its first view with Resume enabled. A link lost during the signal check starts its window again once data flow. Resume is refused while the check is open ("press Done first"), while it settles and while the signal check runs; the overlay grays it out with "The contact check is going off. Resume is possible in a moment." and then "Checking the signal with the contact check off. Sit still. Resume is possible in a moment (N s).". "Check the headset" pressed during the signal check ends it and opens the contact check again. "Check the headset" needs a live link with an open recording: it is grayed out with "Waiting for the headset" while the link is down, and refused by the engine. A link lost while the check is open ends it (`headset_check_end` with `ended_by: "link_lost"`) and the settling waits for the link. Each result is added to `calibration.json` in the list `checks` as a further entry (`kind: "headset_check"`, `states`, `excluded` (the `bad` ones), `measured`, `thresholds_version`, `unix_time`, `utc`, `step`, `reason`, `check`); the calibration step's own result stays as it was at the top of the file, and the session record's `channel_quality_history` lists it first and the checks after it. Skip and Stop close an open check.

**Finishing a block early.** `{"cmd":"block_finished","reason":<reason>,"step":<the round shown>}` ends the running block now; it counts as finished and earns its points, and `block_end` has `ended_by` (the reason) and `seconds`. Two reasons exist: `participant_done` (the participant pressed that they are done; the words agent's recall screens send `{"cmd": "block_finished", "reason": "participant_done"}`), allowed only for a step whose flow entry has `may_finish_early` (in the default flow: `words`, `recall` and `video`), and `trials_done` (the page ran the last trial that fits in the block), allowed for every step of kind `task`. It is refused (`refused`) while nothing runs or the block is paused, for another reason, for a `step` that is no longer the current one, during the calibration parts, and per the rules above. `{"cmd":"video_ended"}` still works as before. **The grace of a task block:** the engine does not end a block of a step of kind `task` that a page module draws (its `module` is not `null`) on its own until its time plus `engine.TASK_GRACE_S` (6 s): the page finishes the trial in progress and sends `trials_done` when no further trial fits. `remaining` is 0 during the grace. A placeholder step (`module` `null`) and the other kinds end at their time as before.

## Participant ID

`brain_mapper.participants.Store(path)` keeps the labels used on this computer in `<data-dir>/participants.json`: `{"version": 1, "participants": [{"label", "uuid"}, ...]}`, most recently used first. `Store.identify(label)` returns the label's identifier, a random UUID4 made the first time the label is used on this computer, and moves the label to the front; the file is written to a new file in the same folder and renamed over the old one. `Store.labels()` lists the labels. `valid(label)` is true for 1 to 32 characters from `A-Z a-z 0-9 _ -` (ASCII only, so path separators, `..`, spaces, control characters and letters or digits from other alphabets are all refused) whose first character is a letter or digit (a name starting with `-` is awkward on a command line). `P001` and `p001` are different labels, so different participants; the page says so when a typed label differs from a remembered one only by case. `Store.peek(label)` gives the identifier a label has or would get without writing anything; `Store.identify(label, fresh=...)` saves a new label with that identifier, and raises `IdentityTaken` (writing nothing) if another label already has it: one identifier is one person under one label. `Store.label_of(uuid)` gives the label that has an identifier, or `None`. The new file is synced and renamed over the old one; the folder is then synced as well, as a best effort (a failure there is logged once and ignored, because the rename has already happened and the file is written). The store assumes one brain-mapper process per data folder: two processes writing at the same moment can lose one another's new label. A file that cannot be read, is not valid JSON, or does not fit the layout (an entry without a UUID, a label that is not allowed, a label twice, another version) raises `StoreDamaged`; its message names the file and says that it has not been changed. The store does not write while the file is damaged.

|Route|Answer|
|-|-|
|`GET /api/participants`|`{"labels": [...]}`; status 500 with `{"labels": [], "error", "code": "store_damaged"}` if the file is damaged|
|`POST /api/participant` with `{"label"}` and optionally `"only"`, `"start_at"` or `"continues"` (see below), or `"import"` (the token of a loaded saved session file, see "Saved session files")|`{"label", "uuid"}`, or `{"error": <words>, "code"}`. The body is read up to 1024 bytes: a declared `Content-Length` above that is refused before anything is read, and a body without a length is abandoned once it passes the limit (the server answers while the client is still sending). Codes: `body_too_large` (413), `bad_body` (400, not a JSON object with a text `label`), `invalid_label` (400, the rule in words), `already_set` (409, the session already has another label; the same label again returns the same answer), `source_not_ready` (409, a replay that could not be opened or did not open within 15 s: the request waits for it up to that long; a live headset is never refused for this, see "Device setup"), `link_ended` (409, the replay has ended), `recording_failed` (500, the recording could not start), `write_failed` (500, the label could not be written to the list), `store_damaged` (500), `internal_error` (500, any other unexpected failure; the traceback is in the server log), and for the extra fields `bad_selection` (400, `only` with `start_at`, or `continues` with either), `unknown_step` (400, an id that is not a round; the answer names the rounds), `not_continuable` (409), `recall_needs_words` (409), and for `import`: `bad_selection` also for `import` with `continues`, `unknown_import` (409, no file loaded with that token in this run), `import_mismatch` (409, the label is not the file's), `participant_conflict` (409, see "Saved session files")|

Accepting a label is all or nothing as far as the session goes: if the recording cannot start, or the label cannot be written to the list, no session exists, the answer is an error (`recording_failed` or `write_failed`) and the label is not accepted. The folder that was made is **kept** (nothing under a session folder is ever deleted) and its `session.json` gets a `failure` with the reason; a later attempt with the same label makes a new folder of its own (`-2` is added if the name is taken). The list is unchanged (a failure is reported only before the list file has been replaced, so a reported failure never leaves the label in it), no session exists and the label can be sent again. The label is written to the list last, so one that never got a session is not offered as "used before". The first accepted label creates the session folder, starts the recording with the label and the identifier (`meta.json` of the recording has `participant` and `participant_uuid`, and the BDF+ header carries the label) and starts the session at its first step. A replayed recording keeps its own `meta.json`; only the session folder and `markers.jsonl` are new. The label is not written to log messages and is not put in a URL. A traceback of an unexpected error may show a session folder path, which contains the label; the log is the standard error of the local brain-mapper process and goes nowhere else.

## Skip, stop, one round, continue

Four abilities of the participant.

**Commands** (from the participant socket only, like the other session commands; before a label is accepted they are refused with "enter a participant ID first"). `{"cmd":"skip"}` ends the current round now: the block in progress is not finished, so it earns nothing (no `points.jsonl` line, no `points` message, `points_total` does not change); blocks of the round that ended earlier keep their points, and the round's outcome follows them as described above (`finished`, `partial` or `skipped`). One `skipped` event and marker (`<step>/skipped#<seq>`) are saved, then the session is at the next step, waiting (a pause is over: `reason` is `null`). It is refused on the `participant` and `device` steps, on the `summary` and once the session is over; the calibration step can be skipped, and so can a paused block. `{"cmd":"skip","step":"<id>"}` skips only if that is still the current step: the page sends the id of the round it shows, so a second press that arrives after the session has moved on skips nothing (`refused`, "no longer the current step"). `{"cmd":"stop"}` ends the session in the ordinary way: one `stopped` event and marker, the recording closed, `stopped` true; nothing is awarded for the block in progress. It is refused before the participant step is done and once the session is over. After a stop every command is refused. `{"cmd":"choose"}` of an earlier draft does not exist (`bad_command`): the choice of rounds travels with the label.

**Chosen rounds, or from a round on.** `POST /api/participant` takes, next to `label`, optionally `only` (a round id, or a list of round ids: those rounds alone, played in route order whatever the order sent) or `start_at` (that round and all later ones), and `continues` (the folder name of an earlier session). `brain_mapper.flow.select(steps, only=None, start_at=None)` keeps the setup steps and the summary and picks the rounds (`flow.chosen(steps, only)` gives the ids of `only` in route order); an id that is not a round raises `ValueError` naming the rounds, an empty list `flow.EmptyChoice` and a round named twice `flow.RepeatedChoice` (both `ValueError`). All of it is checked before anything is created: `only` with `start_at`, or `continues` with either, an empty list ("Choose at least one round, or play the whole route.") and a round named twice are `bad_selection`; an id that is not a round (a setup step, the summary, a text that is none), alone or in the list, is `unknown_step`; a `start_at` or `continues` that is not text, or an `only` that is neither text nor a list of texts, is `bad_body`. Delayed recall as the only round (`only` or `start_at` set to `recall`), or chosen in a list of rounds without the words round before it, is accepted only if some session of this participant (sessions of chosen rounds included) has a `words` round that is `finished` or `partial`, otherwise `recall_needs_words` ("Delayed free recall can be played on its own only after ...", or "... without the Words round only after ..."). The device step and the calibration come before the chosen rounds exactly as before the whole route. The choice stands for the session: the same label sent again with another choice is `already_set` (the same rounds in another order, or one id as a list of one, are the same choice). A session made with `only` is recorded as such (`only` in `session.json`, `progress.json` and the state: the round id when one round was chosen, as before, and a list of round ids in route order when several were) and stands apart from the whole-route sessions: its points total starts at 0 (there is no `carried` line), a round played again that way earns its points again in that session's own ledger, and it is never offered for Continue and never blocks the offer of the participant's earlier whole-route session (the Continue offer, `progress.latest` and the `continues` check look at the newest session made without `only`). A `words` round that is `finished` or `partial` in any session of the participant, one-round or not, counts as studied lists for recall alone, and a session that plays recall without the words round before it (`only` or `start_at` set to `recall`) takes the `seed` of the newest of those sessions (by `started_unix`; `Scan.round_seeds`), so its word lists are the ones the participant studied. Any other new session gets a new seed. `state.plan` and `progress.json` list the steps the session plays.

**`progress.json`** is in the session folder next to `session.json`. The engine writes it by replace-rename when the session begins, whenever what it holds changes (a step or a block boundary, a skip, a stop, the end or a failure) and not for the events of a block, which do not change it: with several hundred events in a block that would be as many fsyncs and renames for nothing. It is written before the page is told of the change. Fields: `version` 1, `session` (folder name), `uuid`, `continues`, `only` (the round id of a one-round session, a list of round ids in route order for several chosen rounds, else `null`; `progress.read` accepts both forms and refuses anything else), `seed` (a whole number made when the session begins, the word-list seed, kept by a continued session), `status` (`running`, `finished`, `stopped`, `ended_early` or `failed`), `plan`, `steps` (`[{id, kind, title, outcome}]` in plan order, outcomes as in `state.outcomes`), `points_total` and `updated_unix`. `brain_mapper.progress` reads it (`read(folder)`, which raises `ProgressDamaged` in words), and `scan(data_dir, uuid)` / `latest(data_dir, uuid)` look through `<data-dir>/sessions/` for the sessions of a participant: whose a session is comes from its `session.json` (`uuid`), never from the folder name. Only the participant's newest session made without `only` (by `started_unix`) can be continued, and only if it has a round `not_reached` (a round that was running when the process died counts as one) and something was played in it (a finished, partly played or skipped round, or points; a session that got no further than the setup is not offered, because starting again is the same). A session that was already continued is not offered again, because the session that continued it is newer. Skipped and partly played rounds stay as they are: continuing offers the rounds of the earlier plan from its next `not_reached` one on, never a skipped, partly played or finished one.

**Damaged or missing files.** A folder whose `session.json` cannot be read or does not name its own folder is described in `Scan.problems` (with its path), is left alone and is not offered. If the newest session of the participant has no `progress.json`, or one that is not valid JSON, not version 1, without a valid step list, or whose `points_total` is not the last total of its `points.jsonl` (or whose ledger does not add up or is missing), `Scan.own_problem` says so in words, there is no session to continue, and the older sessions are not used instead. Nothing in such a folder is changed. The server logs only that some number of session folders could not be read (no path, because a path holds a label); the words go to the page as `note`.

**Continuing.** A `continues` that is not the unfinished newest session of the participant the label belongs to is refused with `not_continuable`, whatever name it carries (another participant's session, an unknown name, a path); the same words are used for all of these. A continued session is a new session folder with its own recording. Its plan is the setup steps, the rounds of the earlier plan from the earlier session's next round on, and the summary. `session.json` and `progress.json` name the earlier session in `continues`; `seed` is the earlier one's. The first line of its `points.jsonl` is `{"seq":1,"step":null,"block":null,"reason":"carried","amount":0,"total":<earlier total>,"carried_from":<earlier session>,"unix_time","sample":null}`, so `state.points_total` starts at the earlier total; no `points` message is sent for it. The ledger accepts a `carried` line only as the first line, with `amount` 0 and a whole `total` of at least 0, and still refuses a file whose other lines do not add up. A round that was stopped before its first block ended is `not_reached`, so continuing plays it from its first block. A round with at least one finished block is `partial` (or `finished`), so continuing starts at the round after it: the blocks it finished earned their points in the earlier session and are not played or paid again, and the blocks it did not play are not played later either.

|Route|Answer|
|-|-|
|`POST /api/progress` with `{"participant": <label>}`|`{"next_step", "next_title", "points_total", "session", "words_done", "note"}`. With an earlier session to continue: its next round (id and title), its points total, its folder name and whether the participant has studied word lists in any earlier session (a `words` round that is `finished` or `partial`). Otherwise `next_step`, `next_title` and `session` are `null`, `points_total` 0: the same shape for a label never used, a label whose only session is the one running now, and one whose record is damaged. `note` is words about a damaged record of this participant's newest session, else `null`. Nothing is written, and nothing is said about any other participant. A label that is not valid is `invalid_label` (400); a body that is not a JSON object with a text `participant` is `bad_body` (400); one that is too long is `body_too_large` (413). The label is in the body and never in a URL, so there is no `GET` for this route (it answers 405).|

Both routes need the Host and Origin of every route and answer 403 otherwise.

## Saved session files

On the Participant ID screen, "Load a saved session file" (a button that opens a file chooser, `#import-choose` and `#import-file`) or a file dropped anywhere on the screen (`#import-box` is marked while one is dragged over) takes the zip a session ended with (see "Session zip"). The page sends the file as the body of `POST /api/import` to this server; the address holds nothing else. The answer fills in the participant ID with the file's (the field is then read-only; "Type an ID instead", `#import-clear`, sets the file aside), and the screen shows `Saved session from <date>: <n> rounds completed` (`#import-summary`; a round is completed when each of its blocks finished), `A new session is saved as sample point <n> for this person.` (`#import-point`) and, when an ID had been typed that is not the file's, `The ID in the file, <file's ID>, is used instead of <typed ID>.` (`#import-label-note`). The main button reads "Start a new session for this person": it sends the file's label with `"import": <token>` (and `only` if a round was chosen on the start screen). Only when the file's own session folder is on this computer and is the person's unfinished newest session (the continue offer of "Skip, stop, one round, continue") is the existing offer shown as well (`#continue-offer`, and a button "Continue from <round>", `#import-continue`, which sends `continues` as before). A refusal is shown in `#import-problem`.

|Route|Answer|
|-|-|
|`POST /api/import` with the zip as the body (`Content-Type: application/zip`)|`{"token", "label", "started_unix", "rounds_done", "rounds_total", "complete", "ending", "points_total", "sample_point", "next_sample_point", "continue"}`; `continue` is `null` or `{"next_step", "next_title", "points_total", "session"}`. Refusals: `{"error", "code"}` with `not_a_zip`, `damaged`, `unsafe`, `not_ours` (400), `too_large` (413), `already_set` (409, a session is under way in this run), `participant_conflict` (409), `store_damaged`, `keep_failed`, `internal_error` (500). The route needs the Host and Origin of every route (a cross-origin page or a foreign `Host` gets 403) and also refuses a peer that is not `127.0.0.1` or `::1`. The body is read in chunks into an anonymous temporary file (it has no name in any folder and is gone when the request ends), never into the data folder; a declared `Content-Length` over the limit is refused before anything is read, and a body without one is abandoned once it passes the limit. The file is checked as untrusted (`brain_mapper.importer.check`); no member is ever written to disk by its name, and nothing from the zip is unpacked into, merged into or changes any session folder.

| Check | Limit |
|-|-|
| Upload size | 1 GiB (`importer.MAX_UPLOAD`) |
| The file | Starts with a zip local header (`PK\x03\x04`) and `zipfile` reads its directory; otherwise `not_a_zip` or `damaged` |
| Members | At most 1000; each name 1 to 512 characters, parts of `A-Z a-z 0-9 _ . -` joined by `/`, no part starting with a dot (so no `..`), no leading `/`, no drive letter, no backslash, no folder entries, no name twice; no symbolic link or other special file (Unix mode bits), no encryption, only stored or deflated; no two members share bytes of the file |
| Sizes | Declared size of each member at most 1 GiB (`MAX_MEMBER`), all together at most 2 GiB (`MAX_TOTAL`); then every member is read to its end in 1 MiB chunks (so its CRC is checked), counting what comes out, and the read stops as soon as a member gives more than it declared or than the limits; a member that gives less than it declared, or fails its CRC, is `damaged` |
| Content | `session.json`, `progress.json`, `events.jsonl`, `points.jsonl` are members, and `<folder>/raw.bin` for each folder in `session.json`'s `recordings`; else `not_ours` |
| `session.json` | At most 8 MiB, UTF-8 JSON (too deep a nesting is `not_ours`); only these fields are used, each checked: `label` (the label rule), `uuid` (a UUID in its canonical form), `session` (`<label>_<YYYYMMDD>_<HHMMSS>[-n]`), `session_id` (16 hex digits or absent), `started_unix` (a number between 1e9 and 1e10), `complete` (true or false), `ending` (one of the endings of "Session zip"), `points_total` (a whole number), `recordings` (at most 100 recording folder names), `flow` (at most 100 steps of `id`, a known `kind`, `title` of at most 200 characters, at most 100 `blocks` with an `id`), `timeline` (at most 100000 entries; `step`, `block` and `outcome` are short text or null), `sample_point` (a whole number from 1 to 100000, 1 if absent) and `previous_sessions` (absent, or at most 1000 entries checked as below) |

A file that passes is copied, byte for byte, to `<data-dir>/imported/<sha256>.zip`: written to `.<sha256>.zip.partial-<8 hex digits>` opened exclusively, synced, read back against its sha256 and given its name with an exclusive rename (never replacing a file); a file already under that name is read and must have that sha256, and is used as it is. Nothing is deleted. The file stays loaded in memory under a random token (the 16 most recent files) until the process ends.

**The person.** Sessions of one person are tied together by the identifier (`uuid`) that `participants.json` gives a label the first time it is used on a computer (see "Participant ID"); `progress.scan` and the sample points look sessions up by it, never by the label. A session started from a file takes the file's identifier, and the label is saved with it in this computer's list if it is new here. So that two people are never joined, a file is refused with `participant_conflict`, when it is loaded and again when the session starts, if this computer's list has the file's label with another identifier, or the file's identifier under another label; on loading, also if a file of the same identifier under another label is already loaded in this run (the check and the registration of the file are one step under one lock). These checks come before anything is looked up by the identifier; nothing is written for a refused file.

**Sample point.** `sample_point` in `session.json` numbers the times a person was measured, as far as this app knows: 1 for a person's first session, and for every later new session one more than the highest sample point among the sessions known for the person, which are this computer's session folders with the same identifier (not those of a start that failed; a folder without the field counts as 1) and, for a session started from a file, the file's session and its `previous_sessions`. A session that continues an earlier one has the same `sample_point` and `previous_sessions` as that one (it is the same measurement, in two folders). One-round sessions count like any other.

| Field of `session.json` | Value |
|-|-|
| `sample_point` | As above |
| `previous_sessions` | The earlier sessions known when the session began, oldest first, one entry per session (by `session_id`, or the folder name for a session made before ids existed): `{"session_id", "session", "started_unix", "start_utc", "sample_point"}`, and `zip_sha256` for a session whose zip was loaded (the sha256 of that file) |
| `imported_from` | Only for a session started from a file: `{"file": "imported/<sha256>.zip", "sha256", "session", "session_id", "sample_point"}` of the loaded file and its session |

All three are written when the session begins and so are in its zip; a zip made before they existed is read with `sample_point` 1 and no `previous_sessions`. With the `zip_sha256` of each entry and the kept copies under `imported/`, the chain of a person's sessions can be checked later. `tests/brain_mapper/fixtures/previous-version-session.zip` is such a zip, made by `scripts/brain_mapper_import_fixture.py` on the code before these fields (a short-flow session on a simulated headset whose channel samples are all zero).

**Privacy.** The label is in the request and answer bodies only, never in an address or a log line (a refusal is not logged; an unexpected failure is logged as in "The log"). The onlooker window is sent nothing of the file: no message about it exists on the websocket. `tests/brain_mapper/test_import.py` and `tests/brain_mapper/test_import_browser.py` cover the route, the refusals (built with `zipfile` and `struct`), the chain of sample points 1, 2 and 3, stopped and ended-early sessions, the log and the onlooker; `tests/brain_mapper/test_no_deletion.py` checks that `importer.py` deletes, replaces and overwrites nothing.

## Points

`brain_mapper.points.Ledger(path)` appends one line per award to `points.jsonl` (in the session folder, next to `events.jsonl`): `seq` (from 1), `step`, `block`, `reason`, `amount`, `total` (after the award), `unix_time` and `sample` (the sample number of the `block_end` marker; the number of samples read if the source had already ended). `Ledger.award(step, block, reason, amount)` returns the new total; `Ledger.total` and `Ledger.awards` give the running total and the awards; reopening the file restores them, and a file whose `seq` or `total` does not follow from the lines before it is refused with `PointsError` (the one exception is a `carried` first line, see "Skip, stop, one round, continue"; `Ledger(path, carried=(total, session))` writes it for a new ledger, `points.read_awards(path)` checks a ledger without opening it). A block that was skipped or stopped writes no line. `award` raises `PointsError` for a step of kind `setup` or `summary`, for an amount that is not a whole number of at least 0, and for any call made while the engine's phase is `running` or `paused`. If a line cannot be written and cannot be taken back out of the file, the ledger is marked unusable and this and every later `award` raises `PointsError`.

When a block ends, `Session` awards `block.points` with the reason `block complete`, in the same all-or-nothing command that ends the block: the marker is put first, then the ledger line is written (a failed write takes the `events.jsonl` line back out; the marker stays in the recording and its `seq` is not reused). The engine hands out the block-end state and then the `points` message before any other command or tick can change the state. `points_total` and `blocks_done` in `state()` change only on the state whose phase is `between` (`blocks_done` also on the paused state of a pause that ended a block, which earns nothing); the `points` message follows that state. Nothing is computed from an EEG measure. During the two rest steps (`kind` is `rest`) a page hides the points total and the progress display; the ledger still records the award.

If the ledger cannot record the award of a block that ended, the block end is not retried: the session ends once, early, with `failure` in `state()` set to `points ledger failed: ...` (phase `done`, `ended_early` true), an `ended` event with that reason is saved, and the recording is closed; the one `block_end` marker already put stays. A client that connects later is told in its first `state`. If a line of `events.jsonl` cannot be written or taken back out, the event log is marked unusable: every later command raises `EventLogFailed` (answered to the page as an `event_log_failed` error) before anything is marked in the recording, and the next tick ends the session once in the same way, with `failure` starting `event log failed` (if the ledger had failed in the same block end, the reason names both). The `ended` event cannot be saved then; the state says it.

Only the participant connection that is the current one can send session commands; a command from a socket replaced by a reload of the same page is not run, even before the server has closed it, and that socket gets `{"t":"error","kind":"replaced"}`.

## Scores

What the page shows as points is the score of each task: the points earned of the points possible, computed from what the participant did. `brain_mapper.scores` computes them, in that one place, from the `<task>.trial` events of `events.jsonl` alone (and, for the video round, the player's `video.*` reports), so the page, `session.json`, `behavior/scores.json` in the zip and a later re-scoring of the folder (`scores.score_folder(folder)`) give the same numbers. Nothing is compared with published data; there are no percentiles. Each rule follows the task's own scoring function in `web/js/tasks/<id>-logic.js` (where the two could differ, the JS definition of a right answer and of the trials left out is the one used; `tests/brain_mapper/test_scores.py` gives the same hand-worked records to both):

| Task | Rule id | Counted (possible) | Earned |
|-|-|-|-|
| Perception, Flanker, Spatial memory | `scored_trials_correct` | Each trial the runner marked `scored` (done, not practice); practice, cut-short, abandoned and failed trials are left out. A trial with no response is counted | `correct` is true |
| 2-back | `nback_answerable_correct` | As above, and only the letters the task's `score` uses: `needs_response` true (not the first two letters of a block or of a run after a resume), not a `tail` letter, a `window_ms` of the full 2400 ms | `correct` is true: `same` on a target, `different` on any other letter; no answer earns nothing |
| Words (immediate recall) | `words_list_recalled` | For each list whose recall trial is `scored`, the distinct words of that list (`words`, 12) | The distinct studied words among the entries (`typed`), each trimmed and lower-cased as `normalize` in `words-logic.js`; a repeat counts once; a word not on the list earns and costs nothing (a word of the other list too). Text left in the field unsubmitted is not an entry |
| Video | `video_10s_watched` | The full 10 s bins of the part played (`start_s` to `end_s` of `video.ready`, from `start_s`: 16 for 11.5 s to 173.5 s) | One point per bin watched: two position reports in a row while playing (`video.play`, `video.progress` or `video.uncover`, then any of those or `video.pause`, `video.ended`, `video.range_end`, each with `seconds`) no more than 2.5 s apart in the video and not backwards mark that stretch as watched; a pause breaks the chain, and a `video.seek` while playing goes on from its `to` (so the page's seek to the start of the part played counts from `start_s`); a bin counts when the stretches cover all of it but at most 0.5 s (the spacing of the reports). A stretch watched twice counts once, so pausing, seeking back or watching again earns nothing twice. No EEG measure is used |
| Delayed recall | `recall_both_lists_recalled` | The distinct words of both lists (`lists`, 24), when the recall trial is `scored` | As for Words, against both lists |

A Words list or the delayed recall whose recall trial was cut short or abandoned (the session was stopped during it, for example) is not counted, as in the runner's rule for every task. The result is `{"tasks": {<task>: {"earned", "possible", "trials", "rule"}}, "total": {"earned", "possible"}}`: a task (keyed by the module of its round) is there once one of its trial events is saved, `trials` is the number of trials (or recalls) counted, and a task with no rule (`example`, `timing`) is not scored. `Session.state()["scores"]` carries it, updated as each trial event is saved (`scores.Scorer`); `session.json` has it as `scores`, and the `BEFORE_ZIP` hook `scores.write_before_zip` writes it to `behavior/scores.json`.

The page shows the scores, not the ledger above: the HUD (`#hud-points`) and the onlooker (`#ol-points`) show the session total as "15 of 64" (a dash before any point was possible); the HUD follows every state, so it changes after each trial, the onlooker never during a running block. The between-blocks screen shows the round's points so far (`#between-gained`, "5 of 12"; for a scored round with nothing counted yet a dash and "No scored trials so far."; a round that is not scored, such as rest, "This round is not scored."; the video round is scored, a point for each full 10 s watched) and the session total (`#between-total`, "15 of 64 points"). The summary lists each scored round, the video included, with "N blocks interrupted by a pause" beside a round a pause cut (`#summary-scores`: title, earned of possible, or a dash with the reason: Skipped, Not reached, Stopped before it started, No scored trials) under the total (`#summary-points`). There are no percentages, ranking words or colors for good or bad. The ledger (`points.jsonl`, `points_total`) still records each finished block as before and is used to continue a session; it is not shown as the participant's points.

## Session zip

Every way a session ends makes a zip of it: finished (Finish on the summary), stopped by the participant, ended early because the headset link or the replay ended, ended by a failure, and the process asked to stop (Ctrl-C or SIGTERM: the source is stopped, the session ends early with the reason `stopped`, and the process waits for the zip before it exits). The recording is closed first, and a recording that was waiting for the headset link is called off, so nothing more is written into the folder. A session whose headset link never came up has no `eeg/`; it is zipped all the same, with what there is. The zip is made on a thread of its own, so the server keeps answering and the websocket keeps its once-a-second state while it is written; files are read and written in chunks, never held whole in memory.

`brain_mapper.package.finish(folder, complete)` makes it in these steps, each of which can be interrupted and done again:

1. The functions in `package.BEFORE_ZIP` are called with the folder: `behavior.before_zip`, which writes `behavior/<task>.csv` and `behavior/columns.json` (see "Tasks", "Behavior files"), then `scores.write_before_zip`, which writes `behavior/scores.json` (see "Scores"). One that raises does not stop the zip: it is named in `hook_errors`, in a log line and in the page's `notes`, and the next one runs.
2. The fields below are added to `session.json` by replace-rename. Every key already there is kept. If the fields are there already (an earlier attempt got this far), the file is left as it is.
3. Every regular file of the folder, at any depth, is listed. Symbolic links (to files or folders) are not followed and not zipped; they, and anything else that is not a regular file, are named in `not_zipped` with the reason. The only regular files left out are the temporary files of an interrupted replace-rename of `session.json` or `progress.json`: at the top of the folder only, and only in the exact shape that writer makes (`.tmp-` + 8 characters from `a-z0-9_` + `.json`); they are named in `not_zipped` too, and a file of any other name or depth is zipped. If anything cannot be listed (a subfolder that cannot be read), the zip is not made at all: the failure is reported like any other, the folder is left as it is, and nothing is zipped in part.
4. The zip is written to `<data-dir>/sessions/.<name>.zip.partial-<8 hex digits>`, created exclusively, and read back: every member to its end (so its CRC is checked), each member's size and sha256 compared with the file listed, and no file listed may be missing. Then it is given its name with a hard link, which fails rather than replace a file, and the temporary name is removed. Where hard links are not possible (a FAT or exFAT disk) the verified file itself is renamed with an exclusive rename (`renamex_np(RENAME_EXCL)` on macOS, `renameat2(RENAME_NOREPLACE)` on Linux), which also fails rather than replace a file. The name is `<folder name>.zip` (`<folder name>_replay.zip` for a replayed recording), beside the session folder; a name that is taken gets `-2`, `-3` ... before `.zip`. An attempt that fails (a full disk, a file size limit, a zip that does not read back the same) removes its own temporary file, the exact path it created, after the failure is logged; the session folder is not touched.
5. `zip` (the zip's file name) is added to `session.json`. A session is packaged once that key is there.

The session folder stays as it is after zipping (earlier sessions are found by their folders). Nothing recorded is overwritten or deleted. The folder is locked (`flock`) from the moment it is made, before `session.json` exists, until its zip is made, with no gap between the session and the zip, so a second process started on the same data folder leaves it alone. If the lock cannot be taken, the page gets an `error` with `kind` `folder_not_locked` and a log line says so.

| Zip member | What it is |
|-|-|
| `session.json` | The session record (below), without `zip` |
| `progress.json`, `events.jsonl`, `points.jsonl` | As in the folder |
| `eeg/raw.bin`, `eeg/recording.bdf`, `eeg/markers.jsonl`, `eeg/meta.json`, `eeg/clock.jsonl` | The recording, as the recorder wrote it; the extracted `eeg/` opens with `open_cognionics.read_recording` and `open_cognionics.replay`, and `recording.bdf` with `mne.io.read_raw_bdf`. Absent when the headset link never came up |
| `eeg-lost-1/...`, `eeg-lost-2/...` | Recordings set aside when a live link was lost before the device step was passed (see "Device setup") |
| `behavior/points.jsonl` | A copy of the folder's `points.jsonl` |
| `behavior/<task>.csv`, `behavior/columns.json` | The behavior files, written just before the zip (see "Tasks", "Behavior files"); no CSV for a task without trial events |
| `behavior/scores.json` | The scores (see "Scores"), written just before the zip; the same as `scores` in `session.json` |
| `calibration.json` and any other file | Every other regular file of the folder, at its path in the folder |

Files of later stages (`audio/`, `analysis/`, `summary.html`, `summary.json`) are absent, not empty. The results (`analysis/`) are computed after the zip is saved and go into an additional zip, `<folder name>-analysis.zip`, beside it (see [brain-mapper results](brain-mapper-results.md)). The session zip never holds `analysis/` (or `analysis-2/` ...): a session zipped again after it is continued leaves those folders out and names them as not zipped, since they have their own zip.

|-|-|
| `participant`, `participant_uuid` | The label and its identifier (the same as `label` and `uuid`) |

Times are from `events.jsonl`; a sample is that of the marker in `eeg/` with the event's `seq`. A step ends where the next one starts or at the event that ended the session. | `channel_quality_history` | `[<content of calibration.json>]` if the folder has `calibration.json`, else `[]` |
| `contact_thresholds_version` | `thresholds_version` of `calibration.json`, else `null`. A `calibration.json` that cannot be read gives `[]` and `null` and is described in `calibration_problem` |
| `points_total` | The total of `progress.json` (the ledger of finished blocks, see "Points") |
| `scores` | Earned of possible per task and in total, from `events.jsonl` (see "Scores") |
| `complete` | `true` only when the participant finished the last step: `session_end` is in `events.jsonl` (Finish was pressed) and `progress.json` says `finished`. A source that ends while the session is at its last step, and an exit whose final tick fails, are not complete |
| `ended_early` | `false` for a finished or stopped session, else `true` |
| `ending` | The `status` of `progress.json` (`finished`, `stopped`, `ended_early`, `failed`), or `interrupted` when it still said `running` (the process died), or `failed_start` for a folder whose start failed (`failure` in its `session.json`; the folder is kept and zipped at the next start) |
| `ending_reason` | The failure, or why the source ended, if the session ended early (for `failed_start`, the `failure` of `session.json`); else `null` |
| `hook_errors` | `[{"hook", "error"}]` for each `BEFORE_ZIP` function that raised: its name, and its error's type and message with paths, the folder name and the label replaced as in the log (below) |
| `not_zipped` | `[{"path", "reason"}]`: each entry of the folder that was not zipped (a symbolic link, a special file, or a temporary file of an interrupted write), with why |
| `replay_of` | Replays only: `{"name"}` of the `--replay` path (`null` in a zip made at start-up) and `raw_sha256`, the sha256 of the replayed `raw.bin` (the copy in `eeg/` is byte for byte the same) |
| `zip` | On disk only, added last: the zip's file name |

**At start-up** (not with `--check`), `brain-mapper` looks through `<data-dir>/sessions/` for session folders without `zip` in their `session.json`: a session whose `progress.json` still says `running` (the process died, for example a kill or a power cut) is zipped with `complete` false, and one whose zip was begun but not recorded (the process died while making it) is zipped as it would have been. A zip already placed under its name but not recorded is checked and taken, so no second zip is made. A temporary zip file left by a crash (`.<name>.zip.partial-<8 hex digits>`, matched exactly to that session's name) is never used; it is removed once a verified zip of that session exists (the zip is read back and compared with the folder), and kept otherwise.

What is printed at start-up, one line each, to the terminal (standard output); each names the session folder (whose name holds the label) and nothing else of the session:

- `brain-mapper: the session <folder> had not been saved as a zip; it is saved now`
- `brain-mapper: the session folder <folder> is from a start that failed; it is kept as it is and saved as a zip now`
- `brain-mapper: <n> temporary zip file(s) of the session <folder>, left by an interrupted run, were removed` (or `were left as they are, because its zip could not be checked`)
- `brain-mapper: the session folder <folder> was not zipped (<reason>); it was left as it is`, for a folder whose `session.json` or `progress.json` cannot be read, whose points ledger does not add up or does not match `progress.json`, or which another brain-mapper process holds (`another brain-mapper process is using it`). The folder is not changed.

**The log.** Nothing written to the `brain_mapper` logger holds a label or a path that contains one: a failure is logged as one line with what failed and the error's type and message, in which every path under the data folder (or the sessions folder), whichever session it belongs to, is replaced by `<data>/...` (from the folder's path up to the next white space or quote), a session folder's name by `<session>` and the labels known there (the one being accepted, the session's) by `<label>`; there is no traceback.

**The page.** When the session is over the server sends `{"t":"package","state":"making",...}`, then `saved` with `file` (the zip's name), or `failed` with `msg` in words (the zip could not be made; the session folder is complete and stays as it is, and the next start makes the zip). `folder` is the sessions folder. `notes` lists, in words, a `BEFORE_ZIP` function that failed and each entry that was not zipped, with the reason. `summary` is `{label, start_local, started_unix, points_total, scores, recordings, awards: [{step, block, reason, amount, total, carried_from}], timeline: [{step, block, start_unix, seconds, outcome}]}`. `download` is the address of the zip, `/api/session/zip?key=<random key>`, and `results` the address of the results with the same key (`/api/results?key=<key>`, see [brain-mapper results](brain-mapper-results.md)), both given only to the participant connection (again after a reload of the participant page); it holds no label. The whole `package` message goes only to the participant connection: an onlooker is never sent it, during the session, after it or on a connection opened after it, because `folder`, `file` and `summary` hold the participant label (`SessionRecord.for_client`; `tests/brain_mapper/test_package.py` and `tests/brain_mapper/test_onlooker_session_end.py` check it with a real onlooker socket and page).

## Tasks

**Registry.** `web/js/tasks/index.js` names the task modules, one line per module in alphabetical order (`export * as nback from "./nback.js";`). A step of kind `task`, `video` or `recall` whose `module` (the step id unless the flow says otherwise) is there shows that module on the `task` screen; one whose `module` is `null` or not registered shows the placeholder. Rest steps (`rest_closed`, `rest_open`, kind `rest`) always keep their own screens. In `default_flow()` the step `video` is of kind `video` and `recall` of kind `recall`, so a module registered as `recall` is shown for the delayed recall step. The step `video` is drawn by the video screen (`screens/video.js`, see "Video" below), not by a task module. A task module is a screen (`mount(root, api)`, `update(state, api)`, `tick(api)`) with `unmount(api)`, which `app.js` calls when the screen is left, and `instructions(blockIndex)`, which the between-blocks screen shows for the next block. The example task (`tasks/example.js`: a square, the space bar, 2 practice trials) and `tasks/timing.js` (30 flashes of 200 ms, onsets 2500 ms apart, nothing to press) are registered there but are played only by test flows.

**Runner.** `tasks/runner.js` makes a task module from a description: `taskScreen({name, keys, legend, block(index), trials(...), run(params, io)})`. Before the first block (phase `waiting`) the screen (`#task-area`, which takes the keyboard focus) shows the title, the block, the instructions (`#task-instructions`), the key legend (`#task-legend`, visible during the trials too) and the leave controls, then a Practice button (`#practice`) when the block has practice trials, then Start (`#advance`). Practice trials run while the engine is still `waiting`. Blocks after the first start from the between-blocks screen, which shows their instructions; only the first block of a round has practice. The engine times the block and the runner runs trials until it ends. `#task-area` carries `data-mode` (`instructions`, `practice`, `trials`, `over`), `data-trial`, `data-practice` and `data-awaiting`. The four F/J tasks (perception, 2-back, flanker, spatial memory) start on Enter instead (see "Start on Enter, the response window and feedback" below).

**Start on Enter, the response window and feedback.** A task defined with `enter: true`, `sides` and `trialMs` (perception, 2-back, flanker and spatial memory) works this way; the example, timing and word tasks keep the buttons described above.
- *The prompt.* Before practice, after practice and before every block, the stimulus area says "Put your fingers on F and J. Press Enter to start." (`#task-enter`, `ENTER_PROMPT`), between the two key labels; above it are the title, "Practice: N trials" or "Block n of N" (`#task-block`) and the instructions (`#task-instructions`; after practice only "Practice is over. The block works the same way."). There is no Practice or Start button. `#task-area` has `data-ready` (`practice`, `block`, or empty). Nothing starts until Enter: any other key does nothing there. Enter starts the practice, or sends `advance`, which starts the block's clock (a second Enter within 1.5 s is not sent again). Between two blocks of the round (phase `between`) `app.js` shows this screen, not the between-blocks screen: the next block's instructions and the prompt; after the round's last block the between-blocks screen comes as before. The task module exports `startsOnEnter: true` for this.
- *Lead-in.* After Enter the stimulus area shows a white fixation cross (`.task-leadin`) for 2000 ms (`LEAD_IN_MS`, inside the block: its clock is already running), logged as `<task>.lead_in` (`duration_ms`, `due_ms` of its end, `frames`, `frame_ms`, `block`, `practice`) at its frame; it goes in the frame of the first change of the first trial, the frame nearest its due end, logged as `<task>.lead_in_end` (`due_ms`, `late_frames`, `frame_ms`, `block`, `trial`, `practice`). Tested in all four tasks: the cross lasted within half a frame of 2000 ms, `late_frames` 0.
- *The response window.* `io.window({ms, from})` opens a window of fixed length from the stimulus onset (`from`, by default the last onset). It ends on the frame grid like a timeout, never on a key. Every F/J press in it is logged as `<task>.resp` (`key`, `response`, `rt_ms`, `index`: 0 for the first press of the trial) and lights its key label; the last press is the answer. The trial record has `response`, `key`, `rt_ms` and `resp_browser_ms` of the last press, `rt_first_ms`, `rt_last_ms` (equal to `rt_ms`), `responses` (the number of presses) and `changed` (true when the first and the last press gave different answers). A press outside the window is a stray key (`<task>.stray`, the first of the trial). What is on the screen during the window is the task's (a 200 ms grating is still 200 ms). Every trial of a task therefore has a fixed length (`trialMs(params)`).
- *Feedback.* At the end of the window, after every trial (practice and blocks), `io.feedback(text, at)` shows "Correct", "Incorrect" or "No response" for 500 ms (`FEEDBACK_MS`) in the frame the window ends (`#task-feedback`, `.task-feedback`, with `data-trial` and `data-practice`), logged as `<task>.stim` with part `feedback` and `feedback` (the text), and its offset as `<task>.stim_off`; the trial record has `feedback` and `feedback_browser_ms`. Then comes the task's gap.
- *The sign that a key was taken.* A press in the window lights its key label (white fill, `.is-pressed`) for 150 ms (`PRESS_SIGN_MS`), the same for either key and whatever the answer.
- *No trial is cut short.* Before a trial starts the runner checks that it ends (its `trialMs`, plus two frames) before the block's nominal end (the end the page reckons from the state); if not, it is not started, the stimulus area goes blank (`data-mode="over"`) and the page sends `{"cmd": "block_finished", "reason": "trials_done"}` once. A server that knows the command ends the block then; one that does not answers with a `bad_command` error, which `app.js` does not show, and the block ends at its time. `cut_short` remains for a block ended from outside.
- *Pause.* A pause abandons the trial in progress (`abandoned`) and the block: its trials never go on (if the block runs again the stage stays blank and the page sends `block_finished`, as above; the runner keeps this per block in its store). The next block starts with its prompt and instructions.
- *Score.* The header (`#hud-points`) shows the server's `state.scores` after every state, so it changes after each trial event ("updated after each trial"); the server sends a state after every event (`engine.event` sets the change flag), so no server change was needed.

A task in full (`tasks/example.js`; a task file of its own plus its line in `index.js` is all a new task needs):

```text
import { el } from "../format.js";
import { taskScreen } from "./runner.js";

export const { mount, update, tick, unmount, instructions } = taskScreen({
  name: "example",                       // event names example.stim, .stim_off, .resp, .stray, .trial
  keys: { Space: "seen" },               // code -> answer: response "seen", key "Space"
  legend: [["Space", "the square is on the screen"]],
  panel: true,                           // the shared stimulus area
  block: () => ({ instructions: "A white square appears ...", practice: 2 }),
  // Once per block (and once for its practice); returns next({index, rng, history}) -> params or null.
  trials: () => ({ rng, history }) => ({
    delay_ms: 300 + rng.int(400),
    done_before: history.length,         // depends on the trials done before it in the block
    response: "space bar",               // a runner field: kept as param_response
  }),
  async run(trial, io) {                 // one trial; what it returns goes into example.trial
    await io.wait(trial.delay_ms);
    await io.show((area) => area.append(el("div", { class: "example-square" })));
    const answer = await io.response({ timeout: 5000 });
    await io.clear();                    // the offset, logged as example.stim_off
    return { correct: answer.answer === "seen" };
  },
});
```

`trials({blockRng, block, blockIndex, practice})` is called once per block and once for its practice; `blockRng` is the same stream every time, so a sequence made from it is the same after a reload, and the `index` given to `next` goes on after a pause or a reload. `next` also gets the trial's own stream `rng` and `history`, the `<task>.trial` payloads of the trials of this block that were `done`, oldest first. The runner keeps `next` and `history` across a pause and a resume; after a reload it calls `trials` again, skips the trials already started (their count is in sessionStorage) and rebuilds `history` from the payloads it stored there, so a task whose trials depend on earlier ones goes on as if nothing had happened; it returns the trial's parameters (they go into `<task>.trial`) or `null` when the block has no more trials. `io` belongs to one trial: `io.area` (the element to draw in, emptied before each trial), `io.clear()` (empties the area in the next animation frame and, if a stimulus was shown, logs `<task>.stim_off` with its `part` and that frame's timestamp; resolves with it), `io.show(draw, extra)` (calls `draw(area)` in the next animation frame, logs `<task>.stim` with `extra` and that frame's timestamp, and resolves with it, the onset; `extra.part` names the part of the stimulus, `stim` if left out, for example `probe` for a second display in the same trial: 1 to 32 of `a-z 0-9 _` starting with a letter), `io.wait(ms, from)` (see "Frame timing"), `io.showAt(dueMs, draw, opts)` and `io.clearAt(dueMs)` (see "Frame timing"), `io.frameMs`, `io.store(key)` (see "Storage"), `io.response({keys, timeout, from})` (resolves `{key, answer, time, rt_ms}` for one of `keys`, by default the task's, `answer` being the task's answer for the key (the code when `keys` is a list), with `rt_ms` counted from `from`, by default the last onset, or `{key: null, ...}` after `timeout` ms), `io.event(what, payload, time)` (logs `<task>.<what>`), `io.index`, `io.practice`, `io.block` and `io.reducedMotion`. When a trial is ended from outside (the block ends, a pause, a skip, a lost connection) every `io` promise it awaits rejects with `Abandoned`, which `run` must not catch; `run` waits only on `io` for its timing.

Each trial is logged with the `event` command, so the server stamps every event with the EEG sample of its marker. A stimulus onset (`<task>.stim`) and offset (`<task>.stim_off`) are the timestamp of the animation frame in which the change is drawn; a response (`<task>.resp`, with `key` as a `KeyboardEvent.code` and `rt_ms`) is the `keydown` event's `timeStamp`; each is the event's `browser_time`. What a trial leaves on the screen when it ends is taken off and logged as `<task>.stim_off` too (see "What stays on the screen"). `<task>.trial` sums up each trial: `response`, `rt_ms` (response time minus the stimulus onset, in ms), `correct`, the trial's parameters, what the task's `run` returned, the timing fields, `block` (the block id), `trial` (its number in the block, which goes on after a pause or a reload), `practice`, `status`, `scored` and `reason`. The timing fields are, for each part shown, `<part>_browser_ms` (its first onset, browser clock) and `<part>_unix_ms` (`time_origin + <part>_browser_ms`, ms since the Unix epoch on the page's clock), and for a response `resp_browser_ms` and `resp_unix_ms`. Measured and runner fields win: a trial parameter named like one of them (`response`, `key`, `cid`, `rt_ms`, `correct`, `block`, `trial`, `practice`, `status`, `scored`, `reason`, `queued` or a timing field) is kept as `param_<name>`, and a field `run` returns with such a name as `result_<name>`, except that `run` may return `correct`, `response`, `key` and `rt_ms` for a trial with no key response (a typed answer), and a returned field with the same value as the runner's keeps its name. `status` is `done`, `cut_short` (the block ended during the trial), `abandoned` (a pause, a lost connection, a skip or a stop, the page closed, full screen closed during practice; `reason` says which: the pause reason, `connection_lost`, `left`, `stopped`, `page_closed`, `fullscreen_lost`) or `error` (the task's code failed); only a `done` trial that is not practice has `scored: true`. A pause abandons the trial in progress and a resume starts a new one; closing full screen during practice stops practice the same way and the instructions come back. Keys: an auto-repeated `keydown` is ignored; a key that is not taken as a response during a trial is logged once per trial as `<task>.stray` (`key`, `awaiting`); `preventDefault` is called only for the task's own keys; a key typed into an input field is left alone, and a key on a button (the leave question's Yes and Keep going, the full-screen overlay) presses the button and is not a response.

**Keys and answers.** `keys` is a list of `KeyboardEvent.code` values, or a map from code to answer (`keys: {KeyF: "left", KeyJ: "right"}`). Every `<task>.trial` and `<task>.resp` record has `key` (the code pressed) and `response` (the answer the map gives, or the code when `keys` is a list), also for a trial abandoned after the press. A task that maps keys itself with a list of keys keeps working as before (`response` is the code, and a `key` it returns with the same value keeps its name).

**Frame timing.** The runner measures the frame period of the display while a task screen is mounted: the median of the last 120 animation-frame intervals, so it follows a 120 Hz or 144 Hz display. The value is kept for the page: a new task screen uses it from its first frame and replaces it only once it has measured 30 intervals of its own (1000/60 ms is used only before the first measurement on the page). `io.frameMs` gives it. `io.showAt(dueMs, draw, opts)` and `io.clearAt(dueMs)` put the change on the frame whose timestamp is nearest to `dueMs` (performance.now clock): the first frame no more than half a frame early, or at once if that frame was missed; they resolve with the frame's timestamp and log `<task>.stim` or `<task>.stim_off` with `due_ms`, `late_frames` (whole frames late: the frames that were due for the change and were dropped before the one that took it; 0 normally. When the runner saw the frame before, which was not yet due, this is the frames that would have come between the two and were due (`missedFrames`), so a change due exactly half-way between two frames, which timestamp jitter of 0.1 ms can put on the later one, 0.503 of a frame after the due time, is not counted late; measured in Chromium at 60 Hz: 8 of 600 such changes went to the later frame, all with nothing dropped. Otherwise it is the frames from the due time to the frame, rounded (`lateFrames`)), `frame_ms` and the frame's time as `browser_time`. `io.wait(ms, from)` counts `ms` as the nearest whole number of frames from `from` when it is given; else from the end of the wait before it (waits in a row add up); else from whichever came last of the last frame painted in the trial (a show or clear) and the end of the last response (the key's time, or the end of its timeout, moved to the frame grid: the last frame painted plus a whole number of frames); else from now. A response ends a wait that was in force before it: in `show; wait(200); response(); wait(1000); clear()` the clear is due 1000 ms after the key, not 1200 ms after the onset, and `late_frames` is counted against that due time. `showAt` and `clearAt` with their own due time are not affected. A response window with a limit (`io.response({timeout})`) ends on the frame grid too: in the frame nearest to `from + timeout` (a key up to then counts), and a `showAt`, `clearAt` or `wait` then `show`/`clear` due in that frame that follows at once is made in that same frame, so a change at onset + limit after a timeout is never a frame late (tested on 20 timeouts in a row, all `late_frames` 0); the next `io.show` or `io.clear` is painted on the frame nearest to the end of the wait and logs `due_ms`, `late_frames`, `frame_ms` and `frames` (the frame count). `wait` resolves up to one frame before the due time, so that the change makes its frame. A 200 ms stimulus is `await io.show(draw); await io.wait(200); await io.clear();` (12 frames at 60 Hz, 24 at 120 Hz, 29 at 144 Hz); anchored onsets are `io.showAt(first + k * spacing, draw)`. The arithmetic is in `tasks/frames.js` (`framePeriod`, `isDueFrame`, `pickFrame`, `lateFrames`, `framesFor`); the tests check it on a frame series recorded in Chromium at 60 Hz and on exact 120 and 144 Hz series (this machine cannot produce those rates), and play 30 stimuli of 200 ms with onsets 2500 ms apart: each lasted 199.9 to 200.0 ms and each onset was within 2.9 ms of its due time, with no drift.

**What stays on the screen.** A trial that is ended from outside (a pause, a skip, a stop, the block's end, the screen left) takes what it drew off the stage at once, so no stimulus stays under the pause overlay or the next screen; its offset is logged as `<task>.stim_off` with the time it was taken off. A trial that finishes leaves the stage to be emptied in the next frame. Something meant to stay up between trials (a fixation cross, a grid) goes in the background layer: `io.background(draw)` draws `draw(layer)` in the next frame into a layer behind the stimuli (`.task-background`, filling the stimulus area), logs `<task>.background` and resolves with the frame's timestamp; the layer stays across trial boundaries, with no frame without it, and is taken away only when a trial is ended from outside, the block is paused, practice stops, or the screen is left. Calling it again replaces what is in the layer. It does not set the frame grid of `io.wait`. The example task draws its fixation cross there once.

**The stimulus area.** `panel: true` in the task definition puts a square stimulus area (`.task-panel`, `#task-panel`) in the center of the dark task screen, with the key legend below it (a task with `sides` has the key labels instead: see below). The area has no ground, border or shadow of its own: every task draws straight on the page's navy (`--stim-ground` in `css/tokens.css`), and its stimuli and text are white (`--stim`; `--stim-soft`, `#d5dbea`, for the recall clock and the field's resting outline). Every color drawn on a task screen is at least 7:1 against the ground it is drawn on (white on the navy `#121826` is 17.7:1, `--stim-soft` 12.8:1; `test_battery_browser.py` computes the ratio of everything drawn in every task from the computed styles). A task screen is exactly as tall as the window, and the stage takes the height that the heading bar, the key legend and the leave controls leave over. The area's side is `min(60vh, 70vw, 760px)` and no larger than the stage (`100cqh`, `100cqw`), held in the CSS variable `--panel` so that what is drawn in it can be sized from it (its font size is `0.12 * --panel`): the area shrinks to make room, the text does not, and the page never scrolls (tested at 1024x768, where the side is 421 px, and at 1920x1080, where it is 648 px, in the instructions, practice, a running block and a pause). The leave controls keep their room while they are hidden in a running block, so the area has the same size in practice and in the block. The area stays while the trials run; `io.area` is the area, and only what is drawn in it comes and goes.

**Key labels.** A task with `sides` (the four F/J tasks) has no legend: the stage holds a row (`.task-row`) of the left key label (`#task-side-left`: "F" and what F means), the stimulus area and the right key label (`#task-side-right`). The key letter is 0.08 of the area's side (at least 28 px), its meaning under it at 0.03 of the side (15 to 32 px). There `--panel` is `min(70vh, 100cqh, 100cqw - 2 x (side + gap), 60vw - 2 x (side + gap))`, with a label `clamp(96px, 7vw, 240px)` wide and a gap of `clamp(16px, 2vw, 64px)`: the labels sit just outside the area and inside the middle 60% of the window's width. Tested at 3840x1600, 1920x1080, 1512x982 and 1024x768 on the prompt and in the lead-in of every task: the labels inside the window, outside the area, level with its middle, within 0.3 of the width from the center, no scroll; at 3840x1600 the area is 1120 px, 0.7 of the height, in a block.

**Storage.** Everything the runner keeps in sessionStorage (trial counts, practice done, the stored history) is under `brain-mapper-task/<session_id>/`, and the events not yet acknowledged under `brain-mapper-task/outbox/<session_id>`, so a later session in the same tab starts clean: when a task screen first sees a session id it removes the runner's stored values of other sessions (not their outboxes, which are sent; see "Delivery"). Task code keeps its own values with `io.store(key)` (in a trial) or `api.store(key)` (anywhere on the page): `{get(fallback), set(value), remove()}` for values JSON can hold, namespaced by the session id and the step. Within a page the runner's memory is the source of truth and sessionStorage only lets a reload go on; if a write to sessionStorage fails (it is full or switched off) the run goes on from memory and the failure is logged once as the event `storage_failed` (`error`, e.g. `QuotaExceededError`).

**Feedback.** Every task that gives feedback uses the same words and look: `feedbackText(answered, correct)` from `tasks/runner.js` gives "Correct", "Incorrect" or "No response" (`FEEDBACK`), and `feedbackNode(text, attrs)` draws it as `.task-feedback` (`css/shell.css`): centered in the stimulus area, white (`--stim`) at 0.06 of the area's side, bold Inter, the same color for every answer, on the page's own navy (`--stim-ground`, so it covers an outline under it without showing a box). `test_battery_browser.py` checks the words and the look in all four tasks.

**Scoring.** A score (points, a summary, feedback) must use only the records with `scored === true`: `done` trials that are not practice. `scoredRecords(records)` from `tasks/runner.js` returns those.

**Payload keys.** No event is lost for its names: the server stores every well-formed event in `events.jsonl` as sent, whatever its payload keys and `part`. A key or part that is 1 to 48 of `a-z 0-9 _` starting with a letter is used as it is for the columns of the behavior files; any other gets a neutral column name there (see "Behavior files"), and the runner writes a console warning once per such key or part, so it shows up in a test run. An event that is not well formed (a bad event name, a payload that is not an object, a time that is not a finite number) is not written; the page gets `{"t": "error", "kind": "bad_event", "cid", "msg"}`, drops it and shows the message. `cid` is the server's: a payload key `cid` of the page's own is stored as `payload_cid`, and a trial parameter or returned field named `cid` becomes `param_cid` or `result_cid`.

**When an event happened.** The server stamps each event with the EEG sample at which it *arrived* (its marker's `sample`), not the sample at which it happened on the page. The true time of an event is its browser time: `browser_time` (`performance.now()` on the page) plus `time_origin` is the event's Unix time in ms on the page's clock. The difference between the server's arrival time and that, `lag_ms = unix_time * 1000 - (time_origin + browser_time)`, is how late the sample is; in the tests on one machine it was at most 15.3 ms for events sent at once (the tests accept up to 250 ms). The sample at which the event happened is about `sample - round(lag_ms * fs / 1000)`, `fs` being the sample rate in `eeg/meta.json`. The two clocks are those of one computer, so this holds to within their drift over a session; the `clock.jsonl` of the recording relates samples to Unix time if a finer correction is needed. An event sent again after the connection was back (`queued: true`) has a lag as large as the outage, and its `sample` must be corrected this way before it is used.

**The times of an event line.** Every line of `events.jsonl` has, read once when the server writes it: `unix_time`, the server's wall clock at arrival in seconds (`time.time()`; the name is kept for the code that reads it), and the same reading as `server_wall_ns`; `server_mono_ns`, the server's monotonic clock at the same moment (`time.monotonic_ns()`); `server_run`, a random id of the server process that wrote the line; and `page_unix_ms`, the page's own time of the event (`time_origin + browser_time`, in ms, on the page's clock; `null` for the server's own events), beside `browser_time` and `time_origin` as sent. The wall clock follows every adjustment of the computer's clock (a time server can set it back or forward by a fraction of a second at any moment), so `unix_time` can go back from one line to the next; the page's clock does not follow such an adjustment made after the page was loaded. Lines are ordered by `seq`. Intervals are measured with the EEG `sample` first (the recording's own clock), then with `server_mono_ns` between lines of the same `server_run` (it never goes back there), never with `unix_time`.

**Delivery.** Every event carries a client id `cid` (the page load's random id and a counter); the server writes it into the payload and answers `{"t": "ack", "cid", "seq"}` once the event is in `events.jsonl`. An event whose `cid` was already written is only acknowledged again, so a copy is never written twice. The page keeps every event that is not acknowledged, in order, in sessionStorage, and after a reconnect or a reload sends them again, in order, with `queued: true`; a new event waits behind them. Each event also carries the page's `session_id`. Events kept for another session (still in the outbox when the server stopped, or when the session ended) are sent too: if that session's folder is on this server, the server appends them to its `events.jsonl` (the next `seq`, `step` and `block` `null`, `late: true` in the payload, no marker, since their sample is unknown) and writes its behavior files again; the answer is `{"t": "ack", "cid", "late": true}`. Every session is zipped as it ends, so such a folder is usually zipped already: the first zip is left exactly as it is, `session.json` counts the events in `late_events_after_zip` (`count`, `first_unix`, `last_unix`, server times of arrival), and at the next packaging (when this server stops, or at the next start) `package.late_zip` runs the before-zip steps again and makes an additional zip `<folder>-late.zip` (then `-late-2.zip` ...), verified like the first, listed in `late_zips` (`zip`, `events`, `hook_errors`). While the folder is being zipped (its lock is held) the event is not answered, so the page keeps it and sends it again after its next reconnect. Otherwise the answer is `{"t": "ack", "cid", "dropped": true}`, and once all of that session's events are answered the page sends one `events_dropped` event in the current session (`count`, `session_id` of the old session, `oldest_browser_ms`, `newest_browser_ms`), which the server also logs (the count only). Neither is shown to the participant. An event refused because the session is over is answered `{"t": "ack", "cid", "refused": "the session is over"}`: the page stops sending it and shows the refusal as a notice. Once the session is over (for example because the headset link ended) the server takes no more events, so the trial that was in progress then is not logged. A command from a participant connection that a newer one of the same page replaced is not run, and that connection gets `{"t": "error", "kind": "replaced"}`. A lost connection abandons the trial in progress and the page shows its connection message; when the connection is back, a block that is still running is paused with the reason `connection_lost`, and the pause overlay says so. A reloaded page pauses a running block (`page_reloaded`) and starts no trial until it is back in full screen.

**Seeded random numbers.** `tasks/rng.js` exports `rng(seed, ...labels)`: the labels (strings or whole numbers) and the seed, written as the JSON text of `[seed, ...labels]`, are hashed with 32-bit FNV-1a over their UTF-8 bytes, and the hash starts a mulberry32 generator. A stream has `next()` (a number in [0, 1)), `int(n)` (0 to n-1, as `Math.floor(next() * n)`; `next()` takes 2^32 values, so each outcome's probability is off from 1/n by less than 1/2^32, a relative error below n/2^32, about 2.3e-8 for n = 100), `pick(list)` and `shuffle(list)` (Fisher-Yates, on a copy). The runner gives each task a stream per block (`rng(seed, name, block, "trials")`, `"practice"` for the practice trials) and one per trial (the same labels and the trial number), so the same session seed gives the same material in every browser and after a reload. `tests/brain_mapper/test_tasks_browser.py` holds the same generator in Python and checks fixed values.

**Behavior files.** When a session ends (finished, stopped, ended early, or ended because the process stopped) `behavior/<task>.csv` and `behavior/columns.json` are written in the session folder just before the zip is made, by the `package.BEFORE_ZIP` hook `behavior.before_zip` (which calls `behavior.write` and logs a failure), so the zip holds them (a session zipped at the next start gets them the same way). There is one CSV file for each task with `<task>.trial` events (`brain_mapper.behavior.write(folder)`, which returns the files written). One row per trial event. Columns: `seq`, `sample` (the EEG sample of the trial event's marker, empty without one), `recording` (the recording folder that marker is in: `eeg`, or `eeg-lost-<n>` for a recording set aside at a lost headset link; sample numbers start at 0 in each recording, so every sample column has a recording column beside it and a sample is read only with it), `unix_time`, `block`, `trial`, `practice`; then for each stimulus part of the task (`stim` first, then the others in sorted order) the part's first `<task>.stim` of the trial: `<part>_seq`, `<part>_sample` (the sample at which it arrived), `<part>_recording` (the recording of that sample: after a drop a trial's stimulus can be in `eeg-lost-<n>` and its response in `eeg`), `<part>_lag_ms` (its lag, see "When an event happened") and `<part>_off_ms` (the first `<task>.stim_off` of that part after it minus its onset, browser clock); then `resp_seq`, `resp_sample`, `resp_recording`, `resp_lag_ms` of the trial's last `<task>.resp`, and `queued` (`true` if the trial event, a stimulus or the response was sent again after the connection was back: correct its samples); then the union of the payload keys of the task's trial events in sorted order (`cid` among them). A payload key named like one of the fixed columns before it is written as `payload_<key>`. The runner sends `block`, `trial` and `practice` in the payload as well: `payload_block`, `payload_trial` and `payload_practice` are left out when they equal the fixed column in every row (if one ever differs it is kept, and the server logs it). A key that follows the rule below keeps its name. A column name that is not 1 to 48 of `a-z 0-9 _` starting with a letter (from a payload key or a part) is written as `x_` and the name in lower case with every other character replaced by `_`, cut to 48 characters (`delayMs` is `x_delayms`, `=cmd` is `x__cmd`, the columns of a part `+x` are `x__x_seq` ...); a neutral name that is already taken gets `_2`, `_3` ... in column order. `behavior/columns.json` lists, for each file, the original name of every column that was renamed (`{"<task>.csv": {"x__cmd": "=cmd"}}`, or `{}` when no column was renamed); it is written with the CSV files every time and never removed. `null` is an empty cell, `true`, `false` and numbers are as in JSON, lists and objects as JSON text, and a text cell, the JSON text of a list or object, and a column name that starts with `=`, `+`, `-`, `@`, a tab or a carriage return gets a `'` in front so that a spreadsheet does not read it as a formula (the neutral names never start with one of those; the guard is kept for every name anyway). The files are built from `events.jsonl` and the `markers.jsonl` of every recording (`eeg-lost-<n>` and `eeg`), written to a new temporary file (`.<name>.<random>.tmp`, removed only if writing it failed) and renamed into place, and an existing file with more rows than the new one is kept. A task whose file cannot be written is logged (with the task's name, without the folder's path) and the other tasks' files are still written; a failure changes nothing else: the session ends normally, the recording and the event log are only read, and the zip is still made (a hook that raises is named in `hook_errors`, see "Session zip").

### Words

Two rounds share `tasks/words.js` (screens) and `tasks/words-logic.js` (pure functions): `words` (title "Words", registered as `export * as words`) and `recall` (Delayed recall, registered as `export { recall }`). In `default_flow()` the step `recall` (kind `recall`, one block of 125 s) shows the `recall` module. Each block is one runner trial. There are no practice trials. Both rounds draw in the shared stimulus area (`panel: true`), which in these two rounds is a centered stage as tall as the shared square and up to 1200 px wide (`.words-task .task-panel`). There is no key legend (`legend: []`): the instructions and the recall prompt say what Enter does, and the finish control carries its own hint. The fixation cross and the word are `min(9vh, 0.2 x --panel)` high (144 px at 3840x1600, 88 px at 1512x982), white on the page's navy; the recall text is sized with `clamp()` from `--panel`; the field has no fill, only a soft white outline (`--stim-soft`).

**Word pool.** `web/assets/wordpool.txt` holds 478 words, one per line in lower case: the noun subset of the Toronto Word Pool as distributed by the University of Pennsylvania Computational Memory Lab. `scripts/brain_mapper_wordpool.py PATH/nouns.txt` writes it from that file (the norms and the header text are not copied). The credit is in `web/assets/CREDITS.md`.

**Lists.** `buildLists(pool, rng(seed, "words", 0))` shuffles the pool and walks it in that order: a word goes to list 1 if list 1 has fewer than 12 words and no word with the same first three letters, otherwise to list 2 on the same terms, otherwise it is passed over. That gives 24 distinct words in two lists of 12. Both rounds use this one draw, so Delayed recall rebuilds the lists from the session seed. A continued session keeps the seed. A session made with Delayed recall alone gets, from the server, the seed of the session in which the participant studied the lists. Either way the lists are the ones studied. Block `list1` studies list 1 and block `list2` studies list 2.

**Jitter.** `drawJitter(rng(seed, "words-timing", <block id>))` draws, in whole ms and uniformly, the blank after each of words 1-11 (`blanks_ms`, 800-1200) and the delay from word 12's offset to the recall cue (`cue_delay_ms`, 1200-1400). The same seed and block give the same jitter, after a reload too. Each word's `words.stim` carries its `blank_ms`, and the trial record carries `blanks_ms` and `cue_delay_ms`.

**Starting with Enter.** The instruction screen of each list says "Watch 12 words, one at a time. Remember as many as you can. Then type the words you remember, pressing Enter after each word." (the count is the list length, `LIST_LENGTH`; the block line above already says "Block 1 of 2"), and just above Start, on its own line, "Press Enter to start." (`#task-enter-line`), the same prompt as the other tasks. The between screen shows list 2's instructions followed by "Press Enter to start.". Enter there, or on the between screen that shows list 2's instructions, presses the screen's Start / Continue button, which starts the block. Delayed recall's instructions are the delayed prompt followed by "Press Enter to start.", and Enter starts it the same way. The key is caught on `window` in the capture phase, so it reaches nothing else, and only one block starts per press because the button disables itself. The block's clock starts with that press, so the time waited before it never shortens study or recall.

**Timeline of a `words` block** (times from Start):
- A fixation cross is shown, its onset being the next frame (F; `words.stim`, part `fixation`, with `lead_in_ms` 2000).
- The 12 words are shown one at a time with `io.showAt` / `io.clearAt`: word p at F + 2000 + (p - n) x 3000 ms + the blanks of the words from n to p - 1, where n is the position the cross led to, and off 3000 ms after that time (part `word`). The word replaces the cross, so the cross has no `stim_off` of its own.
- At word 12's offset + `cue_delay_ms`, the recall cue and the recall view come up in one frame (part `cue`): a row of asterisks, the prompt, the field, the finish control and the clock. A 440 Hz tone of 300 ms plays in that frame (`recall_start.tone` says whether the page's audio was running; the audio is started by the Enter or click that started the block).

The runner puts each change on the frame nearest its due time and logs `due_ms`, `late_frames` and `frame_ms`.

**Recall.** The recall clock starts in the cue's frame and runs for 90 s (`RECALL_MS`; 120 s in Delayed recall), its own clock: it does not depend on how long study took. Only the block's end can cut it (`recallEnd`: at the latest 250 ms before the page expects the block to end, so that the trial record goes out while the block still runs), and then the end says `block_end`. The recall view, top to bottom:
- The cue, "* * * * * * *" (soft white).
- The prompt "Type the words you remember, in any order. Press Enter after each word."
- One text field (`#recall-input`, at most 64 characters) with autocomplete, autocorrect, autocapitalize and spellcheck off.
- "I can't remember any more" (`#recall-done`) with the hint "Tab, then Enter".
- The time left (`#recall-time`, "Time left 1:30"), counting down to the recall end in one style from start to end: nothing changes in the last 10 s.

The entered words are not shown, and nothing says whether an entry is right: each logged entry clears the field and lights its border white with a glow for 200 ms (`LOGGED_MS`, class `words-logged`), the same sign for every entry, a repeated word included. A blank entry is not logged and gives no sign, so Enter on the empty field (twice, or any number of times) does nothing. The field takes the focus back whenever it goes anywhere but the finish controls. Enter submits the text in the field, except while an input method is composing.

**Finishing early.** Tab from the field reaches "I can't remember any more"; Enter (or a click) on it replaces it with "End recall now?" and two buttons, Yes (focused) and Keep going (Tab, then Enter). Yes takes no press for 300 ms after the question appears (`CONFIRM_GUARD_MS`) and no held-down Enter, so a doubled key cannot answer it. Keep going logs `<round>.recall_continue` and puts the focus back in the field; the question logs `<round>.recall_confirm`. Yes ends recall: text still in the field is logged as `unsubmitted` with `ended: "participant"`, `<round>.recall_end` is logged with `ended_by: "participant"` and `recall_ms` (the time from the cue), the trial record goes out, and then the page sends `{"cmd": "block_finished", "reason": "participant_done"}`. The stage then shows only "Waiting for the time to finish" (no field) until the block ends: at once when the engine ends the block on that command, or at the block's time if the engine answers that it does not know the command. When recall ends by its time, the stage shows "Time is up." until the block ends.

Delayed recall (`recall`) has no study phase: after Enter, a 2 s fixation cross (part `fixation`, `lead_in_ms` 2000), then the cue, the tone and the same recall view with the prompt "Remember those lists of words you learned earlier? Type any words you remembered from either list, in any order." (`DELAYED_PROMPT`), 120 s, and the same finish control.

**Word list missing.** If `wordpool.txt` cannot be loaded or yields too few words:
- The stimulus area says "The word list could not be loaded, so this round cannot be played. The block is paused. Choose Skip this round to go on with the next round, or Stop here to end the session."
- The page logs `<round>.pool_failed` (`error`).
- The page pauses the block with the reason "the word list could not be loaded", so the clock stops and the pause overlay offers Skip and Stop. The runner then takes the message off the stimulus area, and the overlay shows the reason.

Resume tries to load the list again.

**Keys.** The task has no keys of its own (`keys: []`), so `response` and `key` are `null` in its records. Letters typed into the field are left alone by the runner, so they never act as F/J or as any other key. A key pressed during study is logged once per trial as `words.stray`.

**Events** (with `block`, `trial`, `practice`):
- `words.stim`: part `fixation` (`list`, `next_position`, `lead_in_ms`), part `word` (`word`, `list`, `position` 1-12, `blank_ms`) and part `cue` (`list`, `segment`), each with the runner's `due_ms`, `late_frames` and `frame_ms`. The onset is its `browser_time`. `recall.stim` has parts `fixation` (`lead_in_ms`) and `cue` (`segment`).
- `words.stim_off`: part `word`, with `due_ms`, `late_frames` and `frame_ms`. When a pause, a skip or a stop cuts a word short, the runner takes it off and logs this event without `due_ms`. Part `cue` is logged when the trial ends and the runner clears the stage.
- `<round>.recall_start`: `segment`, `recall_ms` (the recall time from the cue to the recall end), `tone`, and `list` in Words; its time is the cue's frame.
- `<round>.resp`: per entry, `text` (raw), `first_key_ms`, `enter_ms` (both from that segment's recall start), `segment`, and `list` in Words.
- `<round>.recall_confirm`, `<round>.recall_continue`: `segment` (and `list` in Words).
- `<round>.recall_end`: `segment`, `ended_by` (`participant`, `time`, or `block_end` when the block's end cut the recall clock), `recall_ms` (from the cue), `recall_total_ms` (over the segments), and `list` in Words.
- `<round>.unsubmitted`: text still in the field, with `ended` one of `participant`, `time`, `block_end` or `abandoned`.
- `<round>.pool_failed`: `error`.
- `words.trial`: `list` (the trial's parameter), `words` (studied, in order), `typed` (in order), `matched` (`{text, word, list, position}`), `intrusions`, `intrusions_tagged`, `repeats`, `unsubmitted` (text or `null`), `shown` (`{position, word, visible_ms, cut}`), `blanks_ms`, `cue_delay_ms`, `ended_by` and `recall_ms`. It also carries the runner's fields: `response`, `key`, `rt_ms`, `correct` (all `null`), `fixation_browser_ms`, `fixation_unix_ms`, `word_browser_ms`, `word_unix_ms`, `cue_browser_ms`, `cue_unix_ms`, `cid`, `block`, `trial`, `practice`, `status`, `scored`, and `reason` when the trial was not done.
- `recall.trial`: `lists` (the rebuilt lists), `typed`, `matched` (with the list and position of each), `intrusions`, `intrusions_tagged`, `repeats`, `unsubmitted`, `ended_by` and `recall_ms`, with the same runner fields (`fixation_*` and `cue_*` timing fields).

No field is renamed to `param_` or `result_`.

**Pause.** A pause abandons the trial, and the runner logs it as `abandoned` and empties the stimulus area. The words already shown, the entries made, the recall time used and whether study is over are kept with `io.store` / `api.store` (key `list_<block>`), which is namespaced by the session id and the step. A later session in the same tab, even one with the same seed, therefore starts clean. The page notes how long the word on screen was visible (`shown[].visible_ms`, `cut: true`) and logs text left in the field as `unsubmitted` before the runner ends the trial. On resume, study starts with a new fixation cross and goes on with the next word not yet shown, on the same jitter; a word cut by the pause is not shown again. During recall, a 2 s fixation cross and the cue come again, the field comes back empty (the earlier entries are kept and scored, not shown), a new `recall_start` is logged (the next `segment`), and the recall clock runs for the recall time not yet used. Text left in the field at the pause is not restored.

**Scoring** (`scoreRecall(studied, typed, others)`). An entry matches a studied word if the two are equal after trimming and lower-casing. A later entry of a word already matched is a repeat. Any other entry that is not blank is an intrusion (each time it is typed). There is no fuzzy matching, and raw texts are kept. Immediate recall is scored against the list just studied, so a word from the other list is an intrusion there. `intrusions_tagged` lists each intrusion as `{text, other_list: false}`, or, when it is a word of a list studied earlier in the session (`others`; list 1 for list 2), as `{text, other_list: true, word, list, position}`. For each list the result gives `recalled`, `proportion` (recalled / 12), `by_position` (1 or 0 for each position) and `output_order` (positions in the order recalled). `overall` gives the same over all lists scored (24 for Delayed recall). A summary built from the trial records must take only `scoredRecords(records)` (done, not practice). Ending recall early changes nothing here: possible is still the words studied (12, or 24), and `scores.py` reads the same fields (`words`, `lists`, `typed`, `scored`).

**Tests and screenshots.** `tests/brain_mapper/flows/words.json` (Words 2 x 64 s, so each recall is cut by the block's end after about 11 s; Delayed recall of kind `recall`, 20 s) is the flow most tests in `tests/brain_mapper/test_task_words.py` play. One test plays Delayed recall alone in the default flow (125 s), then a session made with `start_at` set to `recall`; both rebuild the lists studied in the earlier session. One test presses keys while each word is up and in each gap, and checks that every onset and offset is on the frame grid of the fixation at its jittered due time, every word up for 3000 ms in whole frames, and every blank as drawn. `test_task_words_logic.py` checks the constants, the jitter (in range, the same for the same seed), the schedule and that the recall end does not depend on the study's length. `test_task_words_finish.py` checks the Enter start, the double Enter on an empty field, the question, Keep going, the logged end and the `block_finished` command in both recalls, the scores, and a full 145 s block whose recall runs 90 s from the cue with one clock style to the end. `test_task_words_layout.py` checks the instruction, word, recall, question and waiting screens at 3840x1600, 1920x1080, 1512x982 and 1024x768 from their layout boxes. `test_task_words_finish_early.py` checks that the engine ends the block at once on `block_finished`; it is run once the engine knows that command. `scripts/brain_mapper_words_screens.py <out-dir>` plays the flow in Chromium and saves 900x900 screenshots of each screen to a folder outside the repository.

### Perception

`tasks/perception.js` (step id `perception`, 2 blocks of 60 s): orientation discrimination with a staircase. The trial lists, the staircase and the scoring are pure functions in `tasks/perception-logic.js`; the grating is drawn by `tasks/perception-draw.js`; the frame timing is the runner's. Tests: `tests/brain_mapper/test_task_perception_logic.py` (the pure functions and the drawing) and `tests/brain_mapper/test_task_perception.py` (the screen, with the flow `tests/brain_mapper/flows/perception.json`).

**Stimulus.** A canvas fills the shared stimulus area (`panel: true`, side `--panel`), with the key legend below it. It is painted in the page's own ground color, read from the page (`getComputedStyle(document.body).backgroundColor`, the navy `#121826`), so no square shows: the grating appears straight on the dark background. The cross is white (`--stim`). The canvas is in the runner's background layer (`io.background`), so it stays between trials; each part of a trial is painted into it. The canvas's CSS size is the area's width, and its pixel buffer is that width times `devicePixelRatio`. The grating is a Gabor-like patch of light stripes that fade into the ground: a raised sine grating of 3 cycles per 100 CSS px between the background and a light peak color, times a Gaussian window with a standard deviation of 1/6 of the patch width (30% of the canvas). Per color channel, pixel value = background + (peak − background) × window × (1 + cos(2π f u + phase)) / 2, where u is the distance across the stripes; at the window's edge the patch equals the background (pixels beyond 4 standard deviations are the background itself), so the patch has no visible edge, and no pixel is darker than the background. The peak is set by the contrast, 1, and the light color, the white of `--stim` read from the page: per channel peak = background + contrast × (light − background), never below the background, so with contrast 1 the peak of the stripes at the window's center is the light color itself (on `#121826` the stripes rise to `#ffffff`). Contrast is in pixel values, no gamma correction: every trial event has `gamma_corrected: false`, and the colors used are logged as `background_color` and `peak_color` (`#rrggbb`). The grating is a stimulus set by this contrast, not text, so the 7:1 rule for text and symbols does not apply to it. A positive tilt is clockwise on screen (`right`, key J); a negative tilt is counter-clockwise (`left`, key F). The grating is drawn into an offscreen canvas while the cross is on (one canvas and one `ImageData` for the page, reused), and it is copied onto the visible canvas in the frame of its onset.

**Trial.** Every part is shown with `io.show` in an animation frame, and its onset is that frame's timestamp (a `perception.stim` event with `part` set to the part; the runner adds `frame_ms` and, for a part after a wait, `due_ms`, `late_frames` and `frames`):

|Part|`part`|Duration|
|-|-|-|
|Fixation cross|`fixation`|`gap_ms` + 500 ms (`gap_ms` drawn uniformly from the whole ms 600 to 1000), without a break|
|Grating|`grating`|200 ms (its event also has `side`, `tilt_deg`, `signed_tilt_deg`, `phase_deg`, `dpr`, `size_css`, `canvas_px`, `patch_px`, `background_color`, `peak_color`)|
|Blank canvas (the ground)|`blank`|until 1500 ms after the grating's onset: the fixed response window (`io.window`; every F/J press is logged, the last one counts)|
|Correct, Incorrect or No response, after every trial|`feedback`|500 ms from the window's end|

A trial lasts `gap_ms` + 2500 ms (3100 to 3500 ms; `trialMs`). The task starts on Enter with the 2 s lead-in cross (see "Start on Enter"); the canvas's first paint is the cross, in the frame that ends the lead-in. The cross comes up in the first frame after the feedback and stays on, without a break, until the grating. Its onset is logged once. **Frames.** The durations are `io.wait` calls, so each is the nearest whole number of frames of the period the runner measures (`io.frameMs`), counted from the frame of the part before (the blank is put on its due frame with `io.showAt`, so a key pressed while the grating is on, which ends the runner's pending wait, does not shorten the grating): 200 ms is 12 frames at 60 Hz, 24 at 120 Hz and 29 at 144 Hz (201.4 ms). The trial keeps the due times and the whole frames late of the grating and of the blank (`grating_due_ms`, `grating_late_frames`, `blank_due_ms`, `blank_late_frames`), their sum as `late_frames`, and the durations shown (`fixation_ms_shown`, `stimulus_ms_shown`, from the frame timestamps). A press of F or J whose time is before the grating's frame timestamp is a stray key (`perception.stray` with `before_onset: true`), not a response, so `rt_ms` is never below 0. A press while the grating is on counts. The key labels are "F tilted left" and "J tilted right".

**Sides and practice.** Each run of 8 trials has 4 left and 4 right in shuffled order, with no more than 4 of one side in a row. The list has 56 trials, more than fit in 60 s: after the lead-in, 16 to 18 trials fit; one that would not end before the block's end is not started. Before block 1 there are 6 practice trials at 15° (3 left, 3 right). Every trial, practice or not, ends with feedback. Practice does not move the staircase. Block 2's instructions are on the between-blocks screen.

**Staircase.** The tilt starts at 8°. It uses 2-down-1-up: two right answers in a row divide the tilt by 1.26, and a wrong answer or a miss multiplies it by 1.26. The tilt is held within 0.2 to 20°. A trial is a reversal when its step goes the other way from the step before it, and the tilt at a reversal is the tilt that trial was shown at. The staircase moves when a non-practice trial's response window ends (its last press is the answer), before the block's end (the end the runner reckons from the state). An unscored trial changes nothing: practice, a trial abandoned (a pause, a reload, a skip) and a trial cut short by the block's end, even one that was answered, leave the staircase as it was, and the next trial is shown at the same tilt. The state is kept with the runner's task store (`io.store("staircase")`, keyed on the session id and the step), so it carries on from block 1 into block 2 and through a pause or a reload, and a later session in the same tab (even a continued one with the same seed) starts again at 8°.

**`perception.trial` fields** (the columns of `behavior/perception.csv` after the fixed ones). The trial's parameters: `side`, `tilt_deg`, `signed_tilt_deg`, `phase_deg`, `fixation_ms`, `gap_ms`, `stimulus_ms` (200), `response_window_ms` (1500), `contrast` (1: how far the peak goes from the ground toward `--stim`), `cycles_per_100_css_px`, `gamma_corrected` (false), `staircase_trial` (0-based across both blocks; null in practice). The runner's: `response` (`left`, `right` or null for a miss), `key` (`KeyF`, `KeyJ` or null), `rt_ms` (from the grating's onset, never below 0), `correct`, `fixation_browser_ms`, `fixation_unix_ms`, `grating_browser_ms`, `grating_unix_ms`, `blank_browser_ms`, `blank_unix_ms`, `feedback_browser_ms`, `feedback_unix_ms`, `resp_browser_ms`, `resp_unix_ms` (of the last press), `rt_first_ms`, `rt_last_ms`, `responses`, `changed`, `block`, `trial`, `practice`, `status`, `scored`, `reason` and `cid`. What the trial returns, once it is over (not for a trial abandoned before its end): `dpr`, `size_css`, `canvas_px`, `patch_px` (CSS px), `background_color` and `peak_color` (the ground and the peak of the stripes as drawn, `#rrggbb`), `frame_ms` (at the trial's end), `fixation_frame_ms` and `stimulus_frame_ms` (the period used for each wait), `fixation_frames`, `stimulus_frames`, `fixation_ms_shown`, `stimulus_ms_shown`, `grating_due_ms`, `grating_late_frames`, `blank_due_ms`, `blank_late_frames`, `late_frames`, `feedback` (the text shown); a non-practice trial also `reversal` and `next_tilt_deg`. A trial abandoned (or cut short by the block's end before its own end) has only the parameters and the runner's fields; a trial cut short after its end has the returned fields but no `reversal` or `next_tilt_deg`. Each time the canvas is put back in the background layer (the first trial of a block or after a pause) the runner logs `perception.background`. No field is renamed `param_` or `result_`.

**Scoring** (`scorePerception(records)` in `perception-logic.js`; not shown to the participant yet). It uses only the runner's scored records (`scoredRecords`: `done` trials that are not practice); practice, cut-short and abandoned trials enter no measure. The threshold is the geometric mean, exp(mean(ln tilt)), of the tilt at the last 6 reversals of those records, in order of `staircase_trial`. With 2 to 5 reversals it uses all but the first; with fewer than 2 it is null, with `threshold_reason`. The other measures are `n_reversals`, `n_trials`, `accuracy` (correct / n_trials, with a miss counting as wrong) and `median_rt_correct_ms`.

### 2-back

Step id `nback` (`tasks/nback.js`, pure logic in `tasks/nback-logic.js`, style in `css/tasks/nback.css`), 2 blocks of 50 s in the default flow. Letters (B C D F G H J K L M N P Q R S T V W X Z, upper case) appear one at a time in the shared stimulus area (`panel: true`), white on the page's navy, sized from `--panel`, between the key labels "F different" and "J same". From the third letter on, `J` means the same letter as two before and `F` means a different one (`keys: {KeyF: "different", KeyJ: "same"}`). The first two letters of a run need no answer (`needs_response: false`): a press then is logged (`nback.resp`) but never scored, and they get no feedback (the cross stays).

- **Instructions.** Before practice the screen shows the rule in short lines ("Compare each letter with the letter two positions earlier." / "Same: J    Different: F" / "Do not answer the first two letters." / "You can change your answer; your last press counts.") and one worked example in a row (`#task-example`): B, K (no answer), B (J: same as 2 back), F (F: K was 2 back), K (F: B was 2 back), F (J: same as 2 back), with a bracket over the row joining each letter from the third on to the letter two positions earlier (`css/tasks/nback.css`; neighboring brackets at two heights, the higher ones dashed). Then the prompt; Enter starts the practice.
- **Timeline.** One letter every 3200 ms (`TIMING.trialMs`): the letter for 500 ms, then the fixation cross; the answer window is 2400 ms from the onset (`TIMING.responseWindowMs`, `io.window`: every F/J press is logged, the last one counts); at its end, "Correct", "Incorrect" or "No response" for 500 ms; then 300 ms of the cross alone before the next letter. The same in practice and in the blocks. The first letter of a run is shown in the next frame (`io.show`) after the 2 s lead-in. Letter k of the run is asked for at exactly first onset + k × 3200 ms (`io.showAt`), so the schedule does not drift. A run is the block, the practice, or the letters after a reload. The letter goes in the frame nearest its onset + 500 ms (`io.clearAt`, logged as `nback.stim_off`), so a key press while it is up does not shorten it. The white cross is the empty stimulus area's own content (CSS), so it comes on in the frame that takes the letter off (and after the feedback). It is not shown under the pause overlay. A letter is shown only if its whole trial (3200 ms) ends before the block's end (the runner's check). A press after the window is logged as `nback.stray`: the runner logs the first one, `nback.js` logs the rest with `extra: true`.
- **Practice.** Before the first block there are 10 practice letters with 3 targets and one lure of each kind, with the same timeline and feedback as the blocks.
- **Letter lists.** A scored block of the flow (50 s) shows exactly 14 letters (2000 + 14 × 3200 = 46 800 ms; a 15th would end on the block's end). Of the 12 answerable letters, 4 are targets (30 %, rounded). Of the 8 non-targets, 1 is a 1-back lure and 1 a 3-back lure (15 % each, rounded). Tail letters follow: plain non-targets flagged `tail: true`, made on demand from the same stream (`extendTail`), shown only in a block longer than 50 s. They are left out of the scores. Lists are made from the block's seeded stream: `rng(seed, "nback", block, "trials")`, or `"practice"` for the practice list. A lure is never also a target or a lure of the other kind. No letter appears three times in a row, and there are never more than 3 targets in a row.
- **After a pause or a reload.** A pause abandons the trial in progress and the block (see "Start on Enter"); the next block starts with its prompt. A reload starts a new run with the next letter: the first two letters of a run that does not start at the block's first letter are `after_resume: true` and `needs_response: false`, not scored. Later letters are judged only against letters of their own run (`runTrial`), so a 3-back lure whose letter three back came before the reload becomes `lure: null`.
- **Trial event.** `nback.trial` has these fields:
  - the letter: `letter`, `position` (1-based), `needs_response`, `target`, `lure` (`null`, `"1-back"`, `"3-back"`), `tail`, `after_resume`;
  - timing: `scheduled_onset_ms` (null for the first letter of a run), `letter_late_frames`, `frame_ms`, `window_ms`;
  - the answer: `response` (`"same"`, `"different"`, null: the last press in the window), `key` (the code), `rt_ms`, `rt_first_ms`, `rt_last_ms`, `responses`, `changed`, `correct` (null for letters that need no answer and for a trial abandoned before it returned), `feedback` (the text shown, null for a letter that needs no answer), `stray_presses`;
  - the runner's fields: `letter_browser_ms`, `letter_unix_ms`, `feedback_browser_ms`, `feedback_unix_ms`, `resp_browser_ms`, `resp_unix_ms`, `block`, `trial`, `practice`, `status`, `scored`, `reason`, `cid`.

  `nback.stim` has `part` (`letter`, or `feedback`), `frame_ms` and, for a scheduled letter, `due_ms` and `late_frames`; a letter also has `letter` and `position`. `nback.stim_off` marks when the letter or the feedback goes. In `behavior/nback.csv`, `letter_off_ms` is the letter's duration.
- **Scores.** `scores(records)` in `nback.js` is `score(scoredRecords(records))`. It uses only records with `scored: true` (done, not practice). A letter cut short by the block end, answered or not, is recorded as `cut_short` and excluded: it is not a miss. An abandoned letter is excluded too. Of those records, `score` in `nback-logic.js` also leaves out letters that need no answer (including `after_resume`), tail letters, and letters whose `window_ms` is shorter than 2400 ms. It returns:
  - hits and misses (a target answered "different" or not at all counts as a miss);
  - false alarms and correct rejections (a non-target answered "different");
  - the hit rate and the false-alarm rate (an unanswered non-target is not a false alarm);
  - d′ = z(H) − z(F) and c = −(z(H) + z(F)) / 2, where H = (hits + 0.5) / (targets + 1) and F = (false alarms + 0.5) / (non-targets + 1);
  - the median response time of the hits;
  - the false-alarm rate on lures;
  - the number of letters without an answer.

### Flanker

Step `flanker` (`tasks/flanker.js`, pure functions in `tasks/flanker-logic.js`, style in `css/tasks/flanker.css`). A row of five arrows; the answer is the direction of the middle one: `F` left, `J` right (`keys: {KeyF: "left", KeyJ: "right"}`; key labels "F left", "J right"). The flow gives 2 blocks of 50 s. Everything is drawn in the shared stimulus area (`panel: true`): a square SVG field filling it, the middle arrow on the fixation point, white arrows and cross (`--stim`) on the page's navy. The task starts on Enter, with the 2 s lead-in cross. Each trial lasts the same (`trialMs`: 3200 to 3600 ms): a fixation cross (part `fixation`) for 500 ms; the arrows (part `arrows`) for the whole response window of 1500 ms (`io.window`: every F/J press is logged, the last one counts); in the frame the window ends the arrows go and "Correct", "Incorrect" or "No response" (part `feedback`) comes for 500 ms, after every trial; then the stimulus area is cleared (`flanker.stim_off`) for a blank gap of 700 to 1100 ms (a whole number of ms, uniform, from the seeded generator). All timing is the runner's (see "Frame timing"): the arrows come `io.wait(500)` after the cross; the window, the arrows' offset and the feedback are due at the arrows' onset + 1500 ms and made in that frame; the next trial's cross is shown with `io.showAt` at the end of this trial's gap when it follows at once (otherwise, after a reload, in the next frame). The stimulus events carry `due_ms`, `late_frames`, `frame_ms` (and `frames` after a wait) as the runner logs them.

Trials (`blockTrials(rng)`, from `rng(seed, "flanker", block, "trials")`): 40 per block, more than fit in 50 s: after the lead-in, 13 or 14 trials fit, and one that would not end before the block's end is not started. Trials 0-7, 8-15, ... each hold 2 of each combination of congruent (all five arrows the same way) or incongruent (the four outer ones opposite) and middle arrow left or right, shuffled; never more than 3 identical trials in a row. Practice (`practiceTrials(rng)`, before the first block): 6 trials, 3 congruent and 3 incongruent, 3 left and 3 right.

`flanker.trial` holds the trial's parameters `congruent`, `target` and `flankers` (`left` or `right`), `fixation_ms` and `gap_ms`; the runner's `response` (`left`, `right` or null: the last press in the window), `key` (`KeyF`, `KeyJ` or null), `rt_ms` (null for a miss), `rt_first_ms`, `rt_last_ms`, `responses`, `changed`, `correct` (false for a miss); the timing fields `fixation_browser_ms`, `fixation_unix_ms`, `arrows_browser_ms`, `arrows_unix_ms`, `resp_browser_ms`, `resp_unix_ms` (the last press), `feedback_browser_ms`, `feedback_unix_ms`; `feedback` (the text shown); and `block`, `trial`, `practice`, `status`, `scored`, `reason`, `cid`. No field is renamed (`param_` or `result_`). `behavior/flanker.csv` adds, per part, `<part>_seq`, `<part>_sample`, `<part>_lag_ms` and `<part>_off_ms`: `arrows_off_ms` is how long the arrows stayed (the 1500 ms window) and `feedback_off_ms` how long the feedback stayed (500 ms); `fixation_off_ms` is empty, since the arrows replace the cross in the same frame. `score(records)` counts only the records `scoredRecords` keeps (`scored: true`: practice, cut-short, abandoned and failed trials are left out) and gives `n_trials`, `n_misses`, `n_anticipations` (RT under 150 ms) and, for `congruent` and `incongruent`, `n`, `n_correct`, `accuracy` (`n_correct / n`) and `median_rt_ms` (correct trials with RT of 150 ms or more); `flanker_cost_rt_ms` and `flanker_cost_accuracy` are incongruent minus congruent (null when a side has nothing); the accuracy cost is therefore usually negative. Tests: `tests/brain_mapper/test_task_flanker.py` (flow `flows/flanker.json`) and `test_task_flanker_logic.py`; screenshots: `scripts/brain_mapper_flanker_shots.py <out-dir>`.

### Spatial memory

Step id `spatial` (`tasks/spatial.js`, pure functions in `tasks/spatial-logic.js`, styles in `css/tasks/spatial.css`), 2 blocks of 60 s in the default flow, with the key labels "F not filled" and "J filled"; it starts on Enter, with the 2 s lead-in cross (the grid with its own cross comes in the frame that ends it). A square 5 x 5 grid in the stimulus area (`panel: true`), sized from `--panel`, with the key legend below: the squares are white outlines on the page's navy, the squares to remember are filled white, and the probe square has a thicker white outline and a steady glow, with no fill (so it never looks filled). The instructions and the legend speak of "filled" squares; in the events and the trial record a filled square keeps the name `lit` (part `lit`, `lit`, `probe_lit`). The grid and its fixation cross are drawn once in the background layer (`io.background`, logged as `spatial.background`) and stay across trial boundaries in every frame; the stimuli are drawn above them on a second grid of the same size, whose plain center square (the page's navy) hides the cross while the filled squares, the empty grid and the probe are shown, so the cross shows only between trials. One trial, each change on the display frame nearest to its due time (`io.showAt`, `io.clearAt`), every due time anchored to the trial's first frame or to the onset of the filled squares: a fixation cross on the empty grid for `gap_ms` + 500 ms from the trial's first frame, where `gap_ms` (a whole number of ms, uniform in 800-1200) is the jittered gap after the previous trial, run at the start of this one so that an answered trial is not cut short by its gap; then 2, 4 or 6 squares are filled together for 1000 ms; then the empty grid for 2000 ms; then one square is marked (the probe) for the whole response window of 3000 ms (`io.window`: every F/J press is logged, the last one counts; 3000 ms already, so not changed), after which the probe is taken off and, in the same frame, "Correct", "Incorrect" or "No response" comes for 500 ms, after every trial. A trial lasts `gap_ms` + 7000 ms (7800 to 8200 ms, `trialMs`). `J` means "yes, that square was filled", `F` "no, that square was not filled" (`keys: {KeyF: "no", KeyJ: "yes"}`). Practice (before the first block): 3 trials, loads 2, 4, 2 with the probe on a filled, an empty and a filled square. Practice stopped and started again (full screen closed) starts from its first trial again (`practicePicker`).

Trial lists: `blockTrials(gen)` makes 24 trials per block, more than fit (after the lead-in, 7 trials fit in 60 s; one that would not end before the block's end is not started) in two runs of 12, each run holding each of the 6 (load, probe filled or not) combinations twice in shuffled order, so the balance also holds over the blocks; filled squares are drawn without replacement from the 25 cells (numbered 0-24 row by row) and a probe on an empty square from the cells that were not filled. `practiceTrials(gen)` makes the practice. The generators are the runner's block streams (`rng(seed, "spatial", block, "trials")`, one per block id, and `"practice"`).

Events: `spatial.stim` with `part: "lit"` (`load`, `lit`) at the onset of the filled squares; `spatial.stim_off` with `part: "lit"` when they go off; `spatial.stim` with `part: "probe"` (`probe`, `probe_lit`) at the probe onset; `spatial.stim_off` with `part: "probe"` after the answer or the time limit (each with the runner's `due_ms`, `late_frames`, `frame_ms`); `spatial.stim` with `part: "feedback"` (`feedback`) at the end of the window and its `stim_off`; `spatial.resp` for every press in the window (`key` `KeyF` or `KeyJ`, `response`, `rt_ms` from the probe onset, `index`); `spatial.stray` for a key before the probe or after the window. `spatial.trial` has `load`, `lit`, `probe`, `probe_lit`, `gap_ms`, `response` (`"yes"`, `"no"` or null: the last press), `key` (the code, or null), `correct` (false with no answer), `rt_ms` (null with no answer), `rt_first_ms`, `rt_last_ms`, `responses`, `changed`, `feedback`, `feedback_browser_ms`, `feedback_unix_ms`, `fixation_browser_ms` (the trial's first frame), the runner's `lit_browser_ms`, `lit_unix_ms`, `probe_browser_ms`, `probe_unix_ms`, `resp_browser_ms`, `resp_unix_ms`, and `cid`, `block`, `trial`, `practice`, `status`, `scored`, `reason`. `behavior/spatial.csv` adds `lit_seq`, `lit_sample`, `lit_lag_ms`, `lit_off_ms` and the same for `probe`.

Scoring, `score(records)`, uses only records with `scored === true` (the rule of `scoredRecords`), per load: the hit rate H (yes on probes of filled squares), the false-alarm rate F (yes on probes of empty squares), both over answered trials only, the number of trials with no answer, accuracy (right answers over all trials of the load), the median `rt_ms` of right answers and Cowan's K = load x (H - F), null when the load has no answered trial with a filled probe square or none with an empty one; the overall K is the largest per-load K.

`scripts/brain_mapper_spatial_screens.py <out-dir>` saves 900x900 screenshots of the instructions and of each state of a trial.

### Video

Step `video` (kind `video`, one block `video` of 165 s in `default_flow()`), drawn by `js/screens/video.js` with `css/video.css`. It shows Vimeo video 19009646 (spec 6.3) in Vimeo's player, in an iframe (`#video-player`) that is made when the screen is mounted and removed when it is left, so no page loads anything from Vimeo on any other step. The onlooker shows the step title and the time left of the block, never the video. This is the one exception to "nothing is loaded from another host" (spec, section 11: needing the internet for the embedded video is acceptable).

- **Address.** `https://player.vimeo.com/video/19009646?dnt=1&title=0&byline=0&portrait=0&fullscreen=0&controls=0&keyboard=0` (the id is the flow's): Vimeo's own parameters (the player collects no session data or analytics; no title, author or portrait over the video; no full-screen button, since the page is already in full screen; no play bar or buttons, and no keys, so the participant cannot move the play head) and nothing of the session: no label, id, seed or parameter of brain-mapper's own. The iframe has `referrerpolicy="no-referrer"`, so no referrer is sent, and `allow="autoplay"`. The parameters are as described in Vimeo's "Player parameters overview" (help.vimeo.com, article 12426260232977, read 2026-11-25). That article says `controls` needs the video to be "hosted by a Creator, Core, Professional, Studio, or Enterprise account"; on this video it hid every control in headed Chromium on 2026-11-25, and seeking with `setCurrentTime` still worked. Should the controls come back, the page still keeps the play head inside the part played (below). The player loaded and played with `no-referrer` in Chromium on 2026-11-25.
- **Messages.** The page talks to the player with `postMessage`; Vimeo's player.js is not loaded. To the player: `{"method": "addEventListener", "value": <event>}` for `play`, `pause`, `ended`, `timeupdate`, `seeked`, `bufferstart`, `bufferend` and `error` once it is ready, then `{"method": "setCurrentTime", "value": <seconds>}`, `{"method": "play"}` and `{"method": "pause"}` (`setCurrentTime` and `getVideoTitle` are methods of the player.js README; player.js sends a setter as `set` and the property name). From the player: `{"event": <name>, "data": {"seconds", "percent", "duration"}}`, as an object or as JSON text, and `{"event": "ready"}` once it has loaded; a message with `method` instead of `event` is the answer to a call and is ignored. A message is taken only if its `origin` is `https://player.vimeo.com` and its `source` is the iframe's window, so one that the page posts to itself is ignored. The message shapes and event names are those of Vimeo's player.js (github.com/vimeo/player.js: `src/lib/postmessage.js`, `src/player.js` and the event list of its README, read 2026-11-25), and the real player sent them in Chromium on 2026-11-25 (`ready`, `play`, `pause`, `timeupdate` about every 250 ms, `bufferstart`, `bufferend`; `getDuration` answered 180).
- **The round.** Before the block (phase `waiting`): the title, "A short video will play. Watch it as you normally would." (`#video-instructions`), the player, "Loading the video." (`#video-status`) until the player is ready, then Start (`#advance`), and the leave controls. The engine's rules for a block apply as for any round (Start is refused without an open recording on a live link). When the block runs the page asks the player to play: the click on Start (and the one on the start screen) gives the page the user activation that playback with sound needs, and the iframe is allowed to autoplay. If the player has not sent `play` 4 s after that, `#video-hint` says "If the video does not start, click it." A pause of the block (full screen closed, Esc, the connection lost, a reloaded page) pauses the video, and the resume plays it again. The page sends play or pause only when that changes. The round ends at `end_s` (below; the page sends `{"cmd":"video_ended","step":"video"}`, as at the end of the video) or when the block's time is up, whichever comes first.
- **Full window.** From Start on (phases `running` and `paused`, `#video-round[data-full="true"]`) the player fills the whole window (`100vw` x `100vh`; the player letterboxes the video on black), over the HUD (hidden), and the page cannot scroll (`html.video-full`, `overflow: hidden`). It is the page's own full screen: the player's full screen is never used (no `fullscreen` in the iframe's `allow`, `fullscreen=0`), so `document.fullscreenElement` stays the root and nothing pauses the block. "Skip this round" and "Stop here" are in a bar at the bottom (`#video-bar`), shown when the pointer moves, a button is pressed or a key is pressed, and hidden 3 s after the last input (`data-controls` `shown` or `hidden`); they always show before Start, while paused (the pause overlay has its own pair as well), after a player error and with the hint. The server allows a skip or a stop during a running block, so the video round passes `whileRunning` to `leaveControls`. While the player fills the window it takes no pointer events (`pointer-events: none`): a cross-origin frame takes every pointer move, and the page could not see the pointer move; it takes them again while the hint asks for a click.
- **The part played.** `start_s` 11.5 s to `end_s` 173.5 s of the video (`flow.VIDEO`), so neither the opening (a countdown and the title "LXIV", cut to the first picture at 11.2 s) nor the end (a cut to black at 173.7 s, then "Created by Damian Livesey" from 174.5 s and the dedication "In memory of Jack Livesey 1963-2009" from 176.5 s) is seen. The times were read from the player's frames in headed Chromium on 2026-11-25: seeks in 0.5 s steps through 0 to 20 s and 150 to 179.5 s, then 0.1 s steps around each cut; the contact sheets `range-start-sheet.png` and `range-end-sheet.png` (in the shots of this work, outside the repository) show the frames with their times and the chosen one outlined. A black cover (`#video-cover`) hides the player from the start; Start first seeks to `start_s` (`video.seek`, `reason` `range_start`) and then plays, and the cover goes (`video.uncover`) at the first position the playing player reports at or after `start_s` (50 ms short of it counts: a seek can land a frame early). At `end_s` (a timer set from the last position, so the end is not late by the 250 ms between reports) the page covers and pauses the player, logs `video.range_end` and ends the round as the end of the video does. A position before `start_s`, or a jump past `end_s` (a seek), covers the player and sends it back to the last position inside (`video.seek`, `reason` `out_of_range`); it is uncovered once it plays inside again. `#video-round` carries `data-player` (`loading`, `ready` or `failed`).
- **Events** (page events, so each has its marker and EEG sample; `browser_time` is the message's `timeStamp`): `video.ready` with `start_s`, `end_s` and the iframe's size (`frame_css_width`, `frame_css_height` in CSS px, `device_pixel_ratio`); `video.play` with the player's `seconds` and `duration` and the iframe's size; `video.pause` and `video.ended` with `seconds` and `duration`; `video.progress` with `seconds` and `duration`, at most once a second (from `timeupdate`), only while the player is uncovered and inside the part played; `video.seek` (`to`, `reason`); `video.uncover` (`seconds`); `video.range_end` (`seconds`, `end_s`); `video.buffer_start`, `video.buffer_end`; `video.error`, with `reason` `player` (and the player's `name` and `message`) or `not_ready` (and `waited_ms`).
- **`video_ended`.** `Session.video_ended(step)` ends the running block of a step of kind `video` at once. The block counts as finished and earns its points, as at the end of its time, and its `block_end` payload also has `ended_by` (`video_ended`) and `seconds` (how long it ran). It is refused unless a block of a video step is running (not while it is paused), and for a `step` that is no longer the current one.
- **Offline or blocked.** If the player has not sent `ready` 15 s after the iframe was made, the page logs `video.error` (`reason` `not_ready`, `waited_ms` 15000) and shows "The video could not be loaded. Check the internet connection." (`#video-problem`) with Try again (`#video-retry`: a new iframe and a new 15 s wait) and the leave controls ("Skip this round", "Stop here"). There is no Start then, so the session never waits on a player that is not there.
- **Length.** The video is 180 s (the player's `getDuration` and Vimeo's oEmbed `duration`, 2026-11-25). The block lasts 165 s (`flow.VIDEO_SECONDS`): the 162 s played and `flow.VIDEO_MARGIN_SECONDS` (3 s) for the player to start; the click on Start to `video.play` took 0.3 to 0.5 s headed on 2026-11-25.
- **Content-Security-Policy.** The app sets none (no header, no meta tag), so nothing was changed for the player.
- **`--check`.** The `video_host` line (see "Start-up checks").

Tests: `tests/brain_mapper/test_video.py` (the block length and the part played, a flow file's `video`, `video_ended` on a pty device and over the websocket, the `video_host` check) and `tests/brain_mapper/test_video_browser.py` (the screen in Chromium). The video tests need a headed browser and the internet. The tests marked `network` need the internet, are never skipped, and run in a headed Chromium (a window on the screen; Playwright's `headless=False` and nothing else changed: no other user agent, no extra flags): `test_the_real_embed_plays_and_logs_ready_play_progress_pause_and_resume`, `test_the_playing_video_fills_the_window_and_the_controls_come_on_input` (at 1024x768 and 1920x1080), `test_the_end_of_the_part_played_ends_the_round_and_seeks_outside_it_are_pulled_back`, `test_a_whole_session_loads_nothing_from_another_host_outside_the_video_step` and `test_the_video_host_check_passes_when_vimeo_answers` (`uv run pytest -m network` runs them alone). ## The onlooker window

`/onlooker` (`web/onlooker.html`, `css/onlooker.css`, `js/onlooker.js`) is a second window for someone watching. It is not full screen, has no buttons and opens its websocket as `/ws?role=onlooker`. The only command it sends is `{"cmd":"display","on":true}` (again after each reconnect); every session command sent over an onlooker socket is ignored by the server, which `tests/brain_mapper/test_onlooker_browser.py` checks by sending each of them by hand while a block waits and while it runs. Closing or reloading the onlooker window changes nothing in the session or the recording. After the server restarts the window says the connection was lost and opens the socket again every second. The revision guard of the page (a `state` with a lower `rev` than the last is dropped) is reset on every new socket, because a restarted server counts from 0 again; the participant page has the same reset.

What it shows (ids in brackets):

- The step, block, phase, time left, score total (earned of possible, see "Scores") and progress (`#ol-step`, `#ol-block`, `#ol-phase`, `#ol-time`, `#ol-points`, `#ol-progress`). They follow the `state` messages like the participant's HUD: the total changes only when the phase is not `running`. During rest steps the onlooker shows the points and progress that the participant page hides; it shows only the step title, never a task's stimulus or instruction. `#ol-root` carries `data-step`, `data-phase`, `data-kind` and `data-conn`.
- The network view (`#ol-network`), fed by `assets/sample-network.json`, with "Sample data" in its corner badge and in the line under it (`#ol-network-note`) at all times. The score place (`#ol-score`, under the heading "Network score", a plain name chosen here because the spec calls the measure only "segmentation") reads "Score: not measured yet"; no number is shown there.
- The headset (`#ol-fit`) with the contact states (`#ol-contact`). A `{"t":"contact","states":{label: state},"good":n}` message draws the live states ("Live contact check: n of 20 contacts good"; once no `contact` message has come for 3 s it reads "Contact states from the last check, <time> ago: ..."); a `calibration` field of a `state` message (`{"states": {...}}` or the map itself) draws the saved ones ("Saved at calibration: ...") when it changes or when no `contact` message came in the last 3 seconds. Without either the line reads "Contact check not done yet". A real `contact` message without states (the first second after `0x11`, `settling` true) shows "Contact check on: the first measure comes in a second" until the first measure, if no states were shown before; one with `error` shows "Contact cannot be measured: <error>" (`data-source` of `#ol-contact` is `settling` or `error`; otherwise `live`, `last-check` or `saved`). `tests/brain_mapper/test_calibration_zip.py` checks the whole path with the real server: not done yet, settling, the live states of the real messages, then the saved states of the `calibration` field. The server side of both belongs to the calibration task; the tests give the page hand-written messages through `window.__onlooker.onMessage`, which shows what it draws, not that the server sends them (tested after the calibration merge).
- Live traces (`#ol-traces`, the same `TraceView` as the device screen): a ring buffer of 8 seconds, so memory does not grow however long the session runs.
- The link state (`#ol-link`, `data-state`).
- How the session ended (`#ol-ended`, hidden until then; `#ol-root` carries `data-ended`), read from the `state` messages alone: "The session is over: the participant finished it." (`finished`, phase `done`), "The participant stopped the session." (`stopped`) or "The session ended before its last step." (`early`: `ended_early` or a `failure`; the failure text is not shown). The onlooker offers no download and names no zip: it is never sent the `package` message.

The participant's label is not shown: no message sent to an onlooker carries it. If the browser takes a WebGL context back, that view shows "The 3-D view stopped. Trying to bring it back."; when the browser restores the context the view carries on, and if it has not within 3 s the scene is built again, at most 3 times per view, after which the view shows "The 3-D view could not be restarted. Reload this window." The rest of the page keeps working, and no call is made into a view that was taken down (`?restore_ms=N` shortens the 3 s in test mode). With `?test=1` the page exposes `window.__onlooker` (`status`, `fit`, `network`, `errors`, `onMessage`, `sendRaw`) for the tests.

## Device setup

The order of the screens is start, participant ID, device setup. A participant label is accepted whether or not the headset is linked: `Hub.accept` waits up to `Settings.ready_wait` seconds (15) for the first attempt to open a live headset to finish, whichever way it goes, and then makes the session folder and `session.json` as before (all or nothing). If the link is up the recording starts at once, as before. If it is not, the recording starts when the link first comes up, and until it has, the device step cannot be passed (`advance` there is refused with "the headset link is not live yet"). A replay is opened before a label is accepted and is refused with `source_not_ready` if it cannot be.

Events saved before the recording exists, including the `stopped` of a session stopped at the device step before the link came up, have `"marked": false` in their `payload` and no marker, so they have no sample; no round marker can come before the recording, because the engine refuses to start a block or enter a step that has blocks while no recording is open, whatever the flow looks like (see below). If starting the recording fails when the link comes up (for example its folder cannot be made), the session ends once with a plain `failure` ("the recording could not be started (...)"), as other failures do.

Retries. While a live source has never opened, or until the device step has been passed, a failed attempt, or a link that was lost, is tried again 2 seconds after the failed attempt ended; one attempt runs at a time and the retries stop when the process stops. What happens to the recording:

- Never opened, label accepted: there is no recording yet. It starts when an attempt works.
- Never opened, no label: nothing is recorded, nothing is saved.
- Link lost after it was up, before the device step is passed: the library closes the recording at the drop, as for any lost link (the BDF file notes why). The hub renames its `eeg/` folder to `eeg-lost-1/` (`-2` ... for later drops), whole and closed, in the session folder, and when the link is back a new recording starts in `eeg/` (sample numbers start again at 0 in it). The session stays at its step; no `source_ended` event is saved. With no label yet there is no recording to set aside.
- Link lost after the device step has been passed (a drop pauses, it does not end the session): the recording is closed at the drop and set aside as above (`eeg-lost-<n>`, whole and closed, never deleted), and the link is tried again every 2 seconds, with no limit, while the session lasts. `link_lost` gets `last_sample` (the last sample of the closed recording, from the samples decoded while it was open, lost ones included; `null` if not known). A running block, or a running calibration part, is paused with the reason `link_lost` (a `paused` event; the page abandons the trial in progress as for any pause, the block clock stops, the video pauses); the participant page shows the pause overlay with "The headset connection was lost. Wait for it to come back, then press Resume.", what Resume will do (a task block is ended by the pause, as by any pause; see "Pause, the headset check and finishing a block early"), the device tip for the operator (`#fs-lost-tip`) and the leave controls. During the contact check the check starts again from its beginning (a new `contact_start` with `restarted: "link_lost"`). A link lost while a block is already paused, between blocks, waiting or on the summary changes nothing but the link and the gates. When the link is back a new recording starts in `eeg/` (sample numbers from 0; `0x12`, or `0x11` during a contact check, is sent at link-up as before) and `link_back` is saved with `recording` and `first_sample` 0. The block does not resume by itself, not at link-up and not later: while the link is down (the state's `link_down`, from `link_lost` until `link_back`, which comes only once samples flow into the new recording) the overlay's Resume button is grayed out (`disabled`, `aria-disabled="true"`) with "Waiting for the headset" (`#fs-wait`) under it, also when the participant had paused by hand before the drop; it is enabled when `link_back` arrives and the block goes on only when it is pressed. A `resume` sent anyway is refused ("the headset link is not live yet ...") until a recording is open on a live link, and accepted after; a task block then goes on with its remaining time and a fresh trial. A calibration part (eyes open, eyes closed, blinks) cut by the drop starts again from its beginning on resume, since a baseline with a gap is not a baseline: `part_restarted` (`part`, `reason`) and then its `<part>_start` again. Events that arrive while no recording is open are saved as always, without a marker and a sample, with `marked: false` and `no_recording: true` in the payload. "Stop here" during a lost link ends the session in the ordinary way with what was recorded. Markers after the drop go into the new recording; `behavior/<task>.csv` has a `recording` column (the folder of the trial's marker) and the scores count the trials of every recording; `session.json` gets `recording_coverage` (each recording: `folder`, `markers`, `start_unix` and `end_unix` of the events marked in it, and the `blocks` it covers). The zip holds every recording folder. Only the process stopping (Ctrl-C) ends a session on a live source; a replay that reaches its end still ends it early.

Details of the drop. The state of the session is looked at again under the lock that sets a recording aside: once the session is over (stopped, failed, or past the device step) a drop sets nothing aside, a link that comes up later starts no recording for it, and the link is reported as ended. A lost link is tried again 2 seconds after it was lost (`RETRY_SECONDS`), then every 2 seconds after each failed attempt, so a link that keeps dropping neither spins nor makes a recording folder at once for each try. `LiveSource.start_recording` raises `LinkLost` when the link has ended (the reader has finished, or `stop` was called), whether or not the hub has noticed; the hub treats it as a drop (the recording stays promised and starts when the link is back), never as a failure to record. `reset()` closes a recording that is still open. Nothing is ever deleted: a set-aside folder is kept even if it holds no samples, and no code of brain_mapper deletes anything under a session folder except the one folder a refused label made itself (`tests/brain_mapper/test_no_deletion.py` lists every call that can delete, with the reason, and fails on a new one). The 2 second wait bounds what a link that flaps can make: at most one set-aside folder every 2 seconds, so at most 30 a minute. Each drop is one line in `events.jsonl`, `link_lost` (`reason`, `earlier_recording`: the folder that holds the earlier recording or `null`, `decoded_incl_lost`), and each recording that starts after a drop is `link_back` (`recording`, `earlier_recordings`); neither has a marker or a sample. `session.json` gets `recordings`: the set-aside folders in order, `[{"folder": "eeg-lost-1", "decoded_incl_lost": <n>}]`, where `decoded_incl_lost` is the number of samples the library decoded while that recording was open, **including the samples the device reported as lost** (it is `Headset.sample_index`, read just after the recording started, so it can be a few packets short; `null` if not known; informational only). The key is absent while there are none. `link_lost` carries the same figure (`null` when nothing had been recorded on that link). `LiveSource.attempts` holds the start and end of each attempt on `time.monotonic()` (the last 100): successive starts are 1.9 s or more apart and at most 2.0 s plus the earlier attempt's duration plus 0.5 s apart, which `test_source.py` checks.

A silent link is a lost link. A headset that is switched off, runs flat or goes out of range while its dongle stays plugged in does not close the port: reads just find nothing. The hub thread (`Hub._serve`) therefore keeps the time of the last chunk on its own monotonic clock, and when no chunk has come for `SILENT_SECONDS` (3.0 s, in `source.py`; the headset sends 500 samples a second, so 3 s with none is not a gap) on an open live link, it calls `LiveSource.drop_link("silent")`. That closes the port (nothing is written to the headset), the reader ends as when the port fails, and everything above follows through the same path: the recording is closed and set aside whole, `link_lost` is saved with `reason` `"silent"`, `silent_s` 3.0 and `last_sample`, a running block is paused (the page shows the same "headset connection was lost" overlay), the headset is tried again every 2 seconds, a new recording starts at link-up and the block waits for Resume. In the tests the pause came 3.1 s after the last sample on the participant's socket and 3.3 s on the page. A stall shorter than the limit keeps the link; a gap of 1 s or more between two chunks (`STALL_SECONDS`) is saved as `link_stall` (`seconds`, no marker), and in the data the samples due during it show as lost samples (the packet counter counts modulo 128, so the number of lost samples can be smaller than the gap). A link counts as up only once samples flow: `LiveSource.connect_with_retry` calls `open_streaming()`, which after the configuration reply waits up to `SILENT_SECONDS` for the first chunk. A headset that stays silent fails `oc.connect` with `NoData` (about 1.8 s); one that answers and then sends no sample fails the wait (`open_streaming` checks `Headset.sample_index`, so normally there is no wait at all and the recording starts as before); either is one more failed attempt with the `no_data` tip, which makes no recording, no `link_back` and no set-aside folder, and leaves no port or thread open (`tests/brain_mapper/test_silent_link.py` counts both over 50 tries).

No round can start without a recording, whatever the flow: the engine refuses (`CommandRefused`, "the headset link is not live yet ...") to start a block, to enter a step that has blocks, and to leave the `device` step unless a recording is open (and, on a live source, the link has not ended). A skip whose next step has blocks is refused the same way, before anything is written (until 2026-11-25 such a skip ended the session with a failure). Nothing depends on a step named `device` existing: a flow without one cannot start a round before the recording; `tests/brain_mapper/test_link_races.py` leaves the calibration of such a flow both by a measured contact check and by skip. Events written before the first block carry `"marked": false` and no marker in every flow.

`Hub.stop` waits up to 9 seconds for the hub thread, since an attempt to open the headset cannot be interrupted (it normally takes at most about 6.3 seconds, and the library ends it within 8 seconds whatever the device does); the attempt closes its own connection when it finds the hub stopped, and a link that comes up during shutdown starts no recording and writes no failure event. If the hub thread itself fails, the pages get `error` and a `link` with state `ended` and `fault` true (a message of its own, not the dropped-link tip), and a session that exists ends with a `failure`. After such a fault a new label is refused (`source_not_ready`, with the fault text) and nothing is made; the hub is not restarted, so there is no loop: start brain-mapper again.

A replay is never retried. The tip is chosen by what the software sees:

|Seen|`oc` error or state|`data-tip`|Text, in short|
|-|-|-|-|
|No dongle found|`NoHeadset`|`no_headset`|No dongle was found; plug it in, or take it out and plug it in again.|
|More than one dongle|`SeveralHeadsets`|`several_headsets`|The ports are listed; unplug the others or use `--port`.|
|Port cannot be opened|`OpenError`|`open_error`|The error text; another program may be using the port, or the dongle was unplugged.|
|Dongle found, nothing received|`NoData`|`no_data`|Check that the headset is switched on and in range of the dongle.|
|Data arriving, no configuration reply|`NoConfiguration`|`no_configuration`|The headset has not sent its configuration; the cause is not known.|
|Link dropped|`Disconnected` or the end of the source|`dropped`|The link dropped; plug the dongle in again or switch the headset on. Shown while the attempts that follow fail, and on the ended screen after the device step.|
|Samples being lost|`Chunk.lost > 0` in the last 10 seconds|`lost_samples`|The count, that each is a gap in the recording, and to check that the headset is in range of the dongle.|
|An error inside brain-mapper|the hub thread failed (`link.fault` is true)|`fault`|brain-mapper stopped reading the headset because of an error inside it; the session has ended (a session waiting at the device step ends with a `failure`); nothing is tried again.|

The tip goes when the state clears (a link that is live, with nothing lost in 10 seconds). The wording is in `web/js/tips.js`. `NoHeadset` and `SeveralHeadsets` come only from `--port` being left out, which opens a plugged-in dongle, so the tests give the page's tip function the problem that `oc.select_headset` gives for them instead of running the app without `--port`.

`scripts/brain_mapper_device_screens.py <out-dir>` saves a 900 by 900 PNG of each state, made with the pty device, and `tips.txt` with every tip text.

The calibration step (spec 6.3) has these sub-steps, which the engine owns like blocks (`state.substep`):

The page shows the 3-D fit view with the contacts colored by state, "n of 20 contacts are good", the legend (Good, Weak, No contact for `good`, `marginal`, `bad`), and a pill for each contact that is not good (pressing it brings the contact forward). "Check again" (`#check-again`, the command `check_again`) starts the check again: a new `contact_start`, `0x11` again, a new measure. Continue (`#advance`) is enabled once a measure of the check that is on now is in; the engine refuses `advance` before that (after a reload, when the check went off, the screen says "Press Check again").|Continue (`advance`)|

Events and markers of the step (each `calibration/<name>#<seq>` in the recording): `contact_start` (payload `again: true` after Check again), `contact_check_off` (payload `reason`, see below), `contact_end` (payload `excluded`, `good`, `measured`), `settling_start` (payload `settle`, `limit`), `contact_not_off`, `signal_start` (payload `seconds`, `version`), `signal_end` (payload `not_fine`, `fine`, `states`, `error`, `version`), `eyes_open_start` and `eyes_closed_start` (`seconds`), `blinks_start` (`seconds`, `cues`, `gap`, `lead`), `eyes_open_end`, `eyes_closed_end`, `blinks_end`; from the page, `blink_cue` (payload `n`, `of`, `due_s`, its place in the schedule by the engine's clock, `late_ms`, how much later than that it was drawn, and `shown`) with `browser_time` and `time_origin` taken when the cue is drawn, and `tone` (payload `hz`, `ms`, `level`, `audio`: `played` or `unavailable`) when the tone is asked for. Eyes open, eyes closed and blinks run on the engine's clock (`remaining` in the state), so a reloaded page cannot shorten them; leaving full screen pauses them as it pauses a block (markers `paused` and `resumed`), and a page loaded during them pauses with `page_reloaded`. No cue is left out: one drawn late is logged with its `late_ms`; one whose blinks ended before the page could draw it (a page held up) is logged when `done` arrives with `shown` false and `late_ms` `null`; the cues the server has logged in the current blinks are in `state.cues_logged`, so a reloaded page does not send them again. A pause during the blinks ends the page's run of the cues; on Resume it starts again from `cues_logged`, which is empty when a lost link restarted the part (all cues are shown and logged again) and holds the cues already logged after a plain pause (none is shown twice). The step earns no points.

**The signal check** (`brain_mapper/quality.py`, added 2026-11-26). The contact check measures the 125 Hz tone; a channel that carries no tone is called good, so it cannot tell "no tone because the contact is good" from "no tone because none arrived" (a headset that does not make the tone, or a reference or ground electrode without contact, which keeps it off every channel), and it says nothing about the signal once the tone is off. The contact check now says when the tone is not there at all: the `contact` message has `tone_seen`, false when the median over the channels of the tone amplitude is under `contact.TONE_SEEN_V`, 50 uV (in pilot recordings the median with the check on was many times larger, and the tone with it off stayed below this bound), and the contact check then shows "The contact-check tone is not showing on any electrode, so these contact states may be wrong. The signal check after Continue looks at the signal itself." (`#contact-no-tone`; the states and their thresholds are unchanged, and nothing of it is saved). A second check therefore looks at the signal itself, with the tone off and after the settling wait. Per channel, over the 6 s window:

|State|Rule|Where the bound comes from|
|-|-|-|
|`clipped`|more than 1 % of the samples at or within 1 % of the converter's limit|the limit is 2^23 counts times the volts per count (24-bit samples, `docs/protocol.md`, "Scaling"; 833.3 mV at gain 3), as `contact.py` uses; the 1 % share is the analysis's bad-channel rule|
|`flat`|robust standard deviation (1.4826 x median absolute deviation) of the 1 to 45 Hz signal under 0.5 uV|the analysis's bad-channel rule (branch `night-analysis`, `docs/brain-mapper-results.md`, "Bad channels")|
|`noisy`|the 1 to 45 Hz signal over 200 uV peak to peak in more than half of the 1 s pieces (4 or more of 6)|200 uV is the analysis's bound for a bad channel and a rejected segment; 1 s pieces instead of its 2 s segments so that one blink (in at most 2 pieces) does not make a channel noisy in a 6 s window|
|`fine`|none of these||

The 50 and 60 Hz sines are fitted and taken out first, then the line through the first and last samples, then everything outside 1 to 45 Hz is set to zero in the frequency domain (numpy only). Mains pickup is measured (`mains_uv`) and saved but gives no state: no bound for it is established. The bounds have the version `quality.VERSION` (`signal-2026-11-26`). The result is added to `calibration.json` as the field `signal`: `states` (`fine`, `noisy`, `clipped`, `flat` by label), `not_fine` (labels in channel order), `values` (per label `rms_uv`, `ptp_uv`, `mains_uv`, `large_share`, `rail_share`), `version`, `seconds`, `unix_time` (or `error` when more than half of the samples were lost); the other fields are unchanged. The state message carries it in `calibration.signal`; the onlooker shows the same headline under its contact line ("Signal check: ..."). The hub feeds every chunk to a `quality.SignalHolder` (a new `SignalWindow` at each link-up); the engine starts it at `signal_start` and reads it each tick. An engine made without the hub (`signal_window` `None`) goes from settling straight to eyes open, as before.

The tests use synthetic streams in the headset's packet format (`tests/brain_mapper/test_signal_check_browser.py`).

**Start right after a skipped calibration.** Skipping from the contact check leads straight to a round, whose first block also waits for `SETTLE_S` of data with the check off (`_refuse_while_check_goes_off`; the refusal says "the round can start in a moment"). The page does not show that refusal: Start (`#advance`) turns into a disabled "Starting in a moment" (`data-waiting`, `aria-busy`) and the page sends `advance` again every 0.3 s until the round starts or the screen moves on. The recording gate is checked before this one: while the headset link is down, Start is refused with "the headset link is not live yet ...", the page shows that and enables Start again, and nothing is retried, so after the link is back a round starts only on a new press of Start (which may then wait out the settling time as above).

**Dates on screen.** The session record shows times in US order ("November 25, 2026, 4:39 PM"; the timeline "4:39:05 PM"); the data files keep ISO and Unix times. The continue offer on the Participant ID screen names the round it stopped before and no longer shows the ledger's points total. A "the session is over" notice is not shown on the summary or ended screen, where it would cover the record.

**The baseline starts after the check is off.** Eyes open is the resting baseline, so it must not hold the 125 Hz tone or the switch-off transient. After Continue the hub sends `0x12`, and the engine starts `eyes_open` only once the data received since have shown `impedance_on` false for `SETTLE_S`, counted in samples of the data stream: `contact.settle_samples(sample_rate)`, 1000 at 500 samples a second, rounded up at other rates. The hub counts the samples received since the last one that was, or may have been, recorded with the check on (`contact.OffCounter`). A chunk of the stream joins several reads (25 samples or more, more under load) and its `impedance_on` is that of its last sample, so a chunk flagged off that follows one flagged on can begin with samples that were on: the counter takes such a chunk as on up to its last sample, which also covers samples lost between the two. The first eyes-open sample is thus at least 1000 samples after the last sample with the check on, at the cost of at most one chunk of extra wait (before 2026-11-25 the count started at the end of the last chunk flagged on, and eyes open once started 989 samples after the last sample on). A stretch that goes on and off again inside one chunk between two chunks flagged off cannot be seen from the flags the stream gives. In pilot recordings the signal and the tone were back to their resting level within about 1.5 s of a clean switch-off. 2 s is the settling time the thresholds below also leave out. The same rule holds for a round after a contact check (a skip from `contact` leads straight to one): `advance` is refused, with a message, until the data have shown the check off for `SETTLE_S`. A replay is not switched, so there the engine does not wait.

The tone is made in the page with the Web Audio API: a sine of 880 Hz for 500 ms at a gain of 0.3, faded in and out over 20 ms, played when the state moves from `eyes_closed` to `blinks`. A browser starts audio only after a press on the page; any press on the calibration screen starts it. If it has not started, the eyes-open and eyes-closed screens say that no tone will sound and to count to about 20 and look at the screen, which then says "Open your eyes".

**Result.** Continue on `contact` keeps the states of the last second of the check that is on as the result: `calibration.json` in the session folder, written by replace-rename, `{"states": {label: state}, "excluded": [the bad ones, in channel order], "thresholds_version", "unix_time"}`. The state message carries it as `calibration` from then on. A calibration that is skipped before Continue writes no file. (For the session zip: it is the first entry of `channel_quality_history` in `session.json`.)

**The contact check is never left on.** The hub switches it with `Headset.impedance_check` only: `0x11` for each `contact_start` (the state's `contact_check` is the `seq` of the one that is on, else `null`), `0x12` whenever `contact_check` goes `null`. That covers Continue, skip, stop and the end of the session for any reason. A lost link is not covered by that: the `0x12` would go to a port that is gone. What protects the data then is the `0x12` sent each time the link comes up (the test headset also comes on with its check on). `0x12` is also sent when the process stops (Ctrl-C or SIGTERM), and again every 2 s after the last contact byte while the data say the check is on although it should be off (the hub reads what it last switched under its lock, so a Check again at that moment is never undone). When the participant page closes or is reloaded during `contact`, the check goes off (event `contact_check_off`, reason `page_left` or `page_reloaded`) and the screen says to press Check again. No other byte is written, and replays write none.

**The measure.** The tone is at a quarter of the sample rate (`contact.tone_frequency(sample_rate)`, 125 Hz at 500 samples a second, `docs/protocol.md` section 8). Below 280 samples a second the tone would be under 70 Hz, among the brain signal and mains pickup: `tone_frequency` raises `contact.Unmeasurable`, the monitor gives no states and the `contact` message's `error` says why. `brain_mapper.contact.tone_amplitude(data, sample_rate, frequency=125.0)` is the amplitude in volts of the sine at that frequency in each channel of a window (samples by channels; lost samples are left out; the channel mean is removed first), by complex demodulation. `ContactMonitor(config)` leaves out the first second recorded with the check on (the switch-on transient; `settling` is true meanwhile), then keeps the last second (`window_samples(sample_rate)`, a multiple of 4 so it holds whole periods of the tone) recorded with the check on (a chunk with `impedance_on` false empties it and starts the first second again) and gives `states()`, `None` until it has a second. A channel that is flat or touches 99 % of the converter's full scale (2^23 counts, -833.3 mV with the test headset's configuration) is `bad` whatever its tone, because a channel without contact sat at full scale with no tone at all in the pilot recordings. `classify(amplitude, thresholds)` gives `good` below `thresholds.marginal`, `bad` from `thresholds.bad` on, `marginal` between.

**Thresholds** (`contact.THRESHOLDS`, version `provisional-2026-11-25`): `marginal` 1.0 mV, `bad` 4.0 mV of tone. They are provisional, chosen from pilot recordings: no recording says which electrode had good contact, so they rest on an indirect measure, the tone with the check on just before it was switched off set against the 60 Hz pickup in the 10 s just after (2 s settling left out), channel by channel. The pickup rose with the tone, in steps that the two thresholds separate. A poor reference gives low tone and high pickup on every channel at once; a contact measure of each electrode against the reference cannot see that. With the vendor's stated stimulus of 48 nA (`docs/protocol.md`, section 8) 1 mV and 4 mV would be about 21 and 83 kOhm if the amplitude were the vendor's measure; that has not been checked. The version is saved with every session so that sessions can be marked again when the values change.

`scripts/brain_mapper_calibration_screens.py <out-dir>` saves a 900 by 900 PNG of each part (`contact.png`, `contact-focused.png`, `eyes-open.png`, `eyes-closed.png`, `blink-cue.png`, `done.png`) from the pty device, which plays `impedance_on_2s.bin` while the check is on and `onhead_10s.bin` once it is off. The states are those of that recording; no other set of states (all good, for example) can be made from the fixtures.

## Development

The root `pyproject.toml` declares a uv workspace with `brain_mapper` as its member. The `dev` dependency group contains `brain-mapper` and `playwright`, so `uv sync` installs the package, its console command and the test tools.

The browser tests drive Chromium through Playwright. Install the browser once:

```bash
uv run playwright install chromium
```

The tests are in `tests/brain_mapper/`. They start the `brain-mapper` command as a subprocess with `--no-browser`, `--data-dir <temporary folder>` and `--http-port 0`, and pass either `--replay <recording>` or `--port <pty path>`. The pty device is the one in `tests/python/pty_device.py`; the recording is a 15 second recording made from it with `Headset.record`. `test_shell_browser.py` drives the participant page in headless Chromium, which honors `requestFullscreen` from a click and `exitFullscreen()`. `test_scene_browser.py` loads `scene.html` and reads the scene state (object counts, visibility, material colors, uniforms, camera direction). `test_battery_browser.py` checks that every round of `default_flow()` resolves to its registered task module (the video round is drawn by the video screen, not a task module; the rest steps keep their own screens; `recall` is registered with its 120 s block) and plays the whole battery once with `flows/battery.json` (every task with its practice and one short block, Words 30 s so that study ends before recall, then Delayed recall): a scripted participant presses F or J while a task waits for a key and types remembered words, and the test checks the trial events and behavior files of every task, the acknowledgments, the markers, the points and the progress, that every task draws straight on the page (no ground, border or shadow on the stimulus area), that everything drawn on a task screen is at least 7:1 against its ground (WCAG contrast from the computed styles; the ratios are printed), and that the page logged no console warning or error. No test writes a screenshot; the screenshot scripts are in `scripts/` and take an output folder. Run the tests with `uv run pytest tests/brain_mapper`.

`test_whole_session_browser.py` plays a shortened copy of `default_flow()` (the same steps and modules; task blocks of 10 to 30 s, video and rest 2 s, calibration eyes open and closed 3 s) on a pty device that answers the contact-check bytes, with a scripted participant and an onlooker window open throughout. The video round is the real video screen with `player.vimeo.com` aborted in the browser (the offline path, so the test needs no internet): the page says the video could not be loaded and the participant skips the round. The test checks `session.json`, the one recording, the events and markers of every task, the behavior files, `calibration.json`, the scores in `session.json` and `behavior/scores.json` against the trial events counted by hand, the score rows of the summary (none for the video round), the zip and what the onlooker was sent; its other tests check the behavior files in the zip of a stopped and of an ended-early session and when they cannot be written, the one bind path, and the device and calibration steps in front of a one-round session.
